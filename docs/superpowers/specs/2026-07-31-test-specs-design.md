# `--test-specs`: property-based тестване на spec договори — Дизайн

> Дата: 2026-07-31. Статус: одобрен за планиране (auto mode).
> Продължение на ensures/requires. Runtime проверките хващат нарушение само
> ако то се случи при реалното изпълнение. `--test-specs` атакува договорите
> със случайни входове — контрапримерът идва при нас, не в продукция.

## Команден ред

```bash
baga --test-specs file.baga
```

Компилира програмата до C както обикновено, но вместо да изпълнява `main`,
генерира тестов драйвър: за всяка функция със spec, съдържащ `requires` и/или
`ensures`, извиква функцията 100 пъти със случайни аргументи.

## Семантика

- **Генерация на вход:** детерминистичен xorshift64* PRNG с фиксиран seed
  (`0x243F6A8885A308D3`) — повторяеми прогони. `i64` → равномерно в
  [-1000, 1000]; `bool` → 0/1. Други типове (f64, str, Vec, struct, масиви) —
  функцията се пропуска със съобщение (MVP).
- **Requires като филтър:** преди повикването драйвърът оценява requires
  изразите върху генерирания вход (генерира се отделна C функция-предикат
  `b__req_<fn>`). Невалиден вход ≠ бъг — опитва се до 10 пъти нов вход;
  ако не намери валиден, тестът се брои като „пропуснат от requires".
- **Ensures като съдия:** нарушение на ensures по време на тест = контрапример
  → съществуващият `baga_spec_fail` спира програмата с exit 1.
- **Видим контрапример:** в preamble се добавят глобални
  `static int64_t baga_cur_args[16]; static int baga_cur_nargs;` (нули по
  подразбиране). Драйвърът ги пълни преди всяко повикване; `baga_spec_fail`
  печата `  вход: <a0>, <a1>...`, когато `baga_cur_nargs > 0`. Нормалното
  изпълнение не ги пипа — съобщенията са непроменени.
- **Изход на успех:** за всяка функция ред
  `<име>: 100/100 теста минаха (N пропуснати от requires)`, накрая
  `Всички spec тестове минаха. ⚔️`. Ако няма подходящи spec-ове:
  `няма spec-ове за тестване`.

## Пример

```bash
$ baga --test-specs examples/spec_ensures.baga
факториел: 100/100 теста минаха (0 пропуснати от requires)
Всички spec тестове минаха. ⚔️

$ baga --test-specs examples/spec_ensures_fail.baga
spec 'удвой': ensures #1 нарушена: output == 2 * x
  вход: -347
(exit 1)
```

## Бележка за examples/spec_ensures.baga

`факториел(n)` прелива `i64` при `n > 20` — тогава `ensures: output > 0` пада
(математически вярно, но не и за i64). Това е честна демонстрация на
ограниченията на runtime договорите, но прави примера червен. Затова
requires на примера става `n >= 0 && n <= 20` с коментар защо — домейнът на
договора е част от договора.

## Извън обхвата

- Генерация на str/Vec/struct/f64 входове; shrinking на контрапримери;
  конфигурируем брой тестове/seed (фиксирани: 100 и константен seed).
- LLVM backend (той е счупен независимо — отделна тема).

## Тестване

- Зелен: `--test-specs examples/spec_ensures.baga` → 100/100, exit 0.
- Контрапример: `--test-specs examples/spec_ensures_fail.baga` → ensures
  грешка + `вход:`, exit 1.
- Requires филтър: `--test-specs examples/spec_requires_fail.baga` → минава
  (невалидните входове се филтрират; за x≥0 impl връща x≥0).
- Регресия: `make test`; нормалните съобщения на `baga_spec_fail` непроменени.
