# Изпълними spec гаранции (`ensures:`) — Дизайн

> Дата: 2026-07-31. Статус: одобрен за планиране (auto mode).
> Контекст: днес `guarantees:` в spec са свободен текст със статус UNVERIFIED.
> Целта на Бага е „ако имплементацията нарушава гаранция — отказ, не warning".
> Този дизайн прави това реалност чрез runtime проверки, генерирани от компилатора.

## Избран подход

Нова, незадължителна секция `ensures:` в `spec`, съдържаща **булеви изрази на
езика Бага**, разделени със запетаи. Всеки израз е пост-условие, което
компилаторът:

1. **проверява по типове** при компилация (трябва да е `bool`, имената трябва
   да са в scope);
2. **компилира до runtime проверка**, която спира програмата с грешка, ако
   условието е нарушено.

Съществуващата секция `guarantees:` остава непроменена — документация в
свободен текст, печатана от `--specs` и `--proofs`.

### Отхвърлени подходи

- **Евристики върху свободен текст** („output is sorted" → `sorted()`):
  крехко, неявно, против философията „компилаторът е съдия".
- **Формална верификация (SMT solver)**: изисква външна зависимост и е
  несъразмерен обхват; нарушава принципа „нула зависимости". Runtime
  проверките са честната стъпка, която `--proofs` вече предвижда
  („requires formal proof **or testing**").

## Синтаксис

```baga
spec факториел {
    input:
        n: i64
    output: i64
    ensures:
        output > 0,
        n <= 1 || output >= n
}

spec сортирай {
    input:
        arr: i64
    output: i64
    guarantees:                 # остава — свободен текст, документация
        - output is sorted
    ensures:                    # ново — изпълними пост-условия
        output >= arr
}
```

- Секциите в spec могат да са в произволен ред; `ensures:` е незадължителна.
- Изразите се разделят със запетаи (запетаята не е оператор в Бага, така че е
  еднозначен терминатор за `parse_expr`; разделител `-` би се блъскал с
  бинарния минус, затова не се ползва). Позволена е излишна запетая в края.
  Секцията `ensures:` може да се ползва и без `guarantees:`.
- В изразите са видими: **имената на input параметрите** (от spec-а, по
  позиция = аргументите на функцията) и **`output`** — върнатата стойност.
- Допустими са всички изрази на Бага с резултат `bool`: сравнения, `&&`,
  `||`, `!`, извиквания на чисти функции, литерали.

## Семантика

### Проверка при компилация (checker, pass 2)

След съществуващата проверка на сигнатурата spec↔функция:

- всеки `ensures` израз се тип-проверява в scope, съдържат spec input
  имената (с техните типове) и `output: <output тип>`;
- резултатът трябва да е `bool` — иначе грешка:
  `spec '<име>': ensures #N е <тип>, очаквах bool`;
- непознато име → съществуващата грешка `недефинирана променлива '<име>'`;
- `ensures` върху функция, връщаща `void`, е грешка:
  `spec '<име>': ensures изисква функция с върнат тип`;
- spec input, кръстен `output`, при наличие на `ensures` → грешка (конфликт
  със запазеното име).

### Runtime семантика (codegen C)

За функция `f` с `ensures` се генерират две C функции:

```c
static int64_t b__impl_<f>(int64_t n) { /* оригиналното тяло */ }

int64_t b_<f>(int64_t n) {              /* публичното име — wrapper */
    int64_t output = b__impl_<f>(n);
    if (!((output) > 0)) baga_spec_fail("факториел", 1, "output > 0");
    if (!((n <= 1) || ((output) >= n))) baga_spec_fail("факториел", 2, "n <= 1 || output >= n");
    return output;
}
```

- Wrapper-ът носи публичното mangled име (`b_<f>`), така че всички повиквания
  (включително рекурсивните — рекурсията също минава през проверките) са
  покрити. Параметрите на wrapper-а се кръщават с **spec input имената** —
  така `ensures` изразите се emit-ват без преименуване.
- Нов runtime helper в preamble-а:

```c
static void baga_spec_fail(const char *spec, int idx, const char *expr) {
    fprintf(stderr, "spec '%s': ensures #%d нарушена: %s\n", spec, idx, expr);
    exit(1);
}
```

- Проверките са винаги включени (философия: „отказ, не warning"). Без flag
  за изключване (YAGNI).
- Ефекти: wrapper-ът се генерира само в C и има същата сигнатура; ефектовата
  проверка е на AST ниво и не се засяга.

### `--proofs` и `--specs`

- `ensures` изразите се печатат със статус `RUNTIME-CHECKED`;
- `guarantees` си остават `UNVERIFIED — requires formal proof or testing`.

## Засегнати компоненти

| Файл | Промяна |
|---|---|
| `include/baga.h` | Нов `NodeKind NODE_ENSURE` `{ char *ensure_text; Node *ensure_expr; }`; в `NODE_SPEC`: `NodeVec spec_ensures` |
| `src/parser.c` | `parse_spec`: разпознаване на секция `ensures:` → цикъл `parse_expr`, разделени с `,`; текстът на израза се възстановява от токените (span → join) за съобщенията; освобождаване + debug print |

## Извън обхвата (YAGNI)

- LLVM backend (`codegen_llvm.c`) — остава без `ensures`; документирано.
- Self-hosted компилатор (`self/*.baga`) — не добавяме `ensures` там;
  bootstrap компилаторът е референцията.
- Pre-условия (`requires`), invariant-и, formal proof на гаранциите.
- Flag за изключване на проверките.

## Тестване

- Позитивен: `examples/spec.baga` с вярно `ensures` → компилира и работи.
- Негативен (runtime): `spec_ensures_fail.baga` — функция, нарушаваща
  пост-условието → съобщение на български + exit 1.
- Негативен (compile-time): `ensures` с не-булев израз; `ensures` с
  непознато име; `ensures` върху void функция → грешки от checker-а.
- Рекурсия: `факториел` с `ensures output > 0` — проверките важат и за
  вътрешните рекурсивни повиквания.
- Регресия: `make test` (всички съществуващи примери) + `make llvm` ако е
  наличен.
