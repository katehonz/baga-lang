# Пълна проверка на типовете на аргументите при извикване — Дизайн

> Дата: 2026-07-31. Статус: одобрен (auto mode).
> Продължение на typed-vec и vec-generic-syntax.
> Проблем: при извикване на потребителска функция checker-ът проверява
> **само бройката** на аргументите (checker.c, клона „user function" в
> `infer_call`), не и типовете им. `fn f(x: i64)` може да се извика с `str`
> и това мълчаливо „минава" до codegen-а.

## Идея

След проверката на бройката, checker-ът сравнява типа на всеки аргумент с
декларирания тип на съответния параметър. Несъответствие → compile-time
грешка на български.

```baga
fn f(x: i64) -> i64 { return x }

fn main() {
    print(f("текст"))   // ГРЕШКА при компилация:
                        // 'f': аргумент #1 е от тип str, но параметърът е i64
}
```

Инфраструктурата вече съществува:
- `TYPE_FN` пази resolved параметри в `ft->params[j]` (baga.h:371;
  попълват се в `check_program`, checker.c:762-769).
- `type_eq` и `type_str` са доказани — spec checker-ът вече ги ползва за
  същото сравнение (checker.c:834).

Липсва само цикъл в `infer_call` + малък helper за съвместимост.

## Семантика

- **Място:** `infer_call`, клона „user function" (`ft && ft->kind == TYPE_FN`),
  веднага след съществуващата проверка на бройката.
- **Обхват на цикъла:** `min(n->args.len, ft->nparams)` — ако бройката вече е
  грешна, не сравняваме извън наличните аргументи (да не удвояваме грешката
  за бройката с фалшиви типови).
- **Отношение „съвместим" (`type_assignable(arg, param)`):**
  - `TYPE_ERROR` от коятото страна → съвместими (без каскада от грешки).
  - цялочислено семейство: `i32`/`i64` са взаимно съвместими (int литералите
    се инферират като `i64`; няма причина `f(10)` да гърми срещу `i32`
    параметър). `f64` НЕ се бърка с тях — няма имплицитно i64→f64 в codegen-а.
  - иначе → `type_eq(arg, param)` (struct по име, Vec снизходителен при
    неизвестен elem, останалите по kind).
- **Грешка:** `"'%s': аргумент #%d е от тип %s, но параметърът е %s"` —
  български, в стила на съществуващите (`'%s' очаква %d аргумента, получих %d`,
  `vec_push: елемент от тип %s, но векторът е %s`). `check_error` трупа грешки
  (не спира) — всички несъответствия се отчитат.
- **Ефекти върху codegen:** никакви — проверката е изцяело в checker-а;
  двата backend-а (C и LLVM) минават през `check_program` и наследяват
  поведението без промяна.

## Извън обхвата

- Имплицитни числови конверсии при извикване (i64→f64) — codegen-ът не ги
  прави; проверката е строга за не-цялочислени типове.
- Проверка на върнатия тип спрямо контекста на извикването (вече се прави
  отделно за `return`).
- Generic функции (`fn f<T>`) — отделна фича.
- Self-hosted компилаторът да прави същата проверка — отделна задача
  (language parity в self/*.baga).

## Приемливост

- Негативен: `fn f(x: i64)` + `f("текст")` → compile грешка на български,
  exit 1 (и през `baga`, и през `baga-llvm`).
- Позитивен (регресия): всички съществуващи примери и `self/*.baga` се
  компилират без нова грешка (i64 литерали срещу i64 параметри, struct по име,
  `Vec<i64>`/`Vec<str>` срещу съвместими Vec параметри).
