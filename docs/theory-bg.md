## 1. Основи на Теорията на Типовете

### 1.1 Просто типизирано ламбда смятане

В основата на Бага лежи просто типизираното ламбда смятане (Church, 1940;
Curry & Feys, 1958). То се определя от три множества:

**Терминове** (програми):

```
t ::= x                    променлива
    | λx:T. t              абстракция (функция)
    | t₁ t₂                апликация (извикване)
```

**Типове**:

```
T ::= B                    базов тип (i64, f64, str, bool)
    | T₁ → T₂             функционален тип
```

**Съждения за типизиране**:

```
Γ ⊢ t : T
```

където Γ е *контекст на типизиране* — крайно множество от допускания от вида
`x : T`. Съждението се чете: „в контекст Γ, термът t има тип T".

Правилата за извод са:

```
───────────── (Var)        Γ(x) = T
Γ ⊢ x : T

Γ, x : T₁ ⊢ t : T₂
───────────────────── (Abs)
Γ ⊢ λx:T₁. t : T₁ → T₂

Γ ⊢ t₁ : T₁ → T₂    Γ ⊢ t₂ : T₁
────────────────────────────────── (App)
Γ ⊢ t₁ t₂ : T₂
```

Тези три правила са достатъчни, за да се гарантира, че всяка добре типизирана
програма е *силно нормализируема* — т.е. всяка редукция завършва. Това е
теоремата за прогрес и запазване (Wright & Felleisen, 1994):

**Теорема (Прогрес).** Ако `∅ ⊢ t : T`, тогава или t е стойност, или съществува
t′ такова, че `t → t′`.

**Теорема (Запазване).** Ако `Γ ⊢ t : T` и `t → t′`, тогава `Γ ⊢ t′ : T`.

### 1.2 Съответствието на Къри-Хауард

Съответствието на Къри-Хауард (Curry, 1934; Howard, 1980) установява изоморфизъм
между:

| Програми | Логика |
|---|---|
| Типове | Предложения (формули) |
| Терминове | Доказателства |
| Изчисление (β-редукция) | Опростяване на доказателство |
| Функционален тип `A → B` | Импликация `A ⊃ B` |
| Произведение `A × B` | Конюнкция `A ∧ B` |
| Сума `A + B` | Дизюнкция `A ∨ B` |
| Празен тип `⊥` | Противоречие |

В контекста на Бага това означава: когато компилаторът приеме една програма,
той е приел и *конструктивно доказателство* за съответната логическа формула.
Функцията:

```baga
fn идентичност(x: i64) -> i64 {
    return x
}
```

е доказателство за твърдението `∀x: i64. ∃y: i64. y = x` — тривиално, но
конструктивно.

### 1.3 Разширението на Бага: ефекти върху типове

Класическото съответствие на Къри-Хауард разглежда само *чисти* изчисления.
Бага го разширява, като въвежда **ефектови анотации** върху типовете:

```
T !E₁ !E₂ ... !Eₙ
```

Това не е синтактична захар. `str !IO !NotFound` е *различен тип* от `str`.
Два израза с еднаква стойност, но различни ефектови множества, са несъвместими
без явна обработка.

От гледна точка на Къри-Хауард, ефектовата анотация `!E` съответства на
*модален оператор* в логиката:

```
◇_E P  ≡  „P е възможно при наличие на ефект E"
```

Типът `str !IO` се чете: „стойност от тип str, чието получаване изисква
взаимодействие с външния свят". Това е по-слабо от чистото `str`, но по-силно
от пълното мълчание за странични ефекти.

### 1.4 Формална граматика на типовете в Бага

Пълната граматика на типовете:

```
T ::= i64                          64-битово цяло число
    | f64                          64-битово число с плаваща запетая
    | str                          низ (UTF-8)
    | bool                         булева стойност
    | [T]                          динамичен масив (вектор)
    | &T                           заемка (reference)
    | Идентификатор                потребителски тип (struct, enum)
    | T !E₁ !E₂ ... !Eₙ           ефектов тип

E ::= IO                           вход/изход
    | NotFound                     ресурсът не е намерен
    | Permission                   отказан достъп
    | Div                          деление на нула
    | E_потребителски              потребителски ефект
```

Ефектовият тип `T !E₁ ... !Eₙ` се интерпретира като наредена двойка `(T, {E₁, ..., Eₙ})`,
където вторият компонент е *множество* — редът на ефектите е без значение:

```
str !IO !NotFound  ≡  str !NotFound !IO
```

### 1.5 Правила за типизиране на конструкциите в Бага

**Let-свързване:**

```
Γ ⊢ e : T
────────────────────────── (Let)
Γ, x : T ⊢ body : T′
──────────────────────────
Γ ⊢ let x = e; body : T′
```

Пример:

```baga
let x = 42          // Γ ⊢ 42 : i64, следователно Γ, x : i64 ⊢ ...
let y: f64 = 3.14   // явна анотация: Γ ⊢ 3.14 : f64
```

**Функция:**

```
Γ, x₁ : T₁, ..., xₙ : Tₙ ⊢ body : T_ret !E₁ ... !Eₖ
────────────────────────────────────────────────────────── (Fn)
Γ ⊢ fn f(x₁: T₁, ..., xₙ: Tₙ) -> T_ret !E₁ ... !Eₖ : unit
```

Пример:

```baga
fn факториел(n: i64) -> i64 {
    if n <= 1 {
        return 1
    }
    return n * факториел(n - 1)
}
```

Тук `Γ, n : i64 ⊢ body : i64`, следователно `Γ ⊢ факториел : i64 → i64`.

**Условен израз (if):**

```
Γ ⊢ cond : bool    Γ ⊢ t₁ : T    Γ ⊢ t₂ : T
────────────────────────────────────────────── (If)
Γ ⊢ if cond { t₁ } else { t₂ } : T
```

И двата клона трябва да имат *един и същ* тип T. Ако единият клон има ефекти,
те се добавят към ефектовото множество на целия израз.

**Цикъл (while):**

```
Γ ⊢ cond : bool    Γ ⊢ body : unit
──────────────────────────────────── (While)
Γ ⊢ while cond { body } : unit
```

Цикълът винаги има тип `unit` — той не връща стойност. Променливите,
модифицирани в тялото, трябва да са декларирани с `let mut`.

**Съпоставка с образец (match):**

```
Γ ⊢ e : T_e
Γ ⊢ pᵢ : T_e    Γ ⊢ eᵢ : T    за всяко i ∈ {1, ..., n}
────────────────────────────────────────────────────────── (Match)
Γ ⊢ match e { p₁ => e₁, ..., pₙ => eₙ } : T
```

Всички клонове на match трябва да имат един и същ тип. Пример:

```baga
let резултат = match n {
    0 => 100,
    1 => 200,
    2 => 300,
    _ => 999,
}
// Γ ⊢ резултат : i64
```

### 1.6 Извеждане на типове

Бага използва опростен алгоритъм в стила на Hindley-Milner (Milner, 1978;
Damas & Milner, 1982). Основните стъпки:

1. **Генериране на ограничения.** Обхождане на AST-то и генериране на
   уравнения между типови променливи:
   ```
   Γ ⊢ e : α    →    α = i64   (ако e е литерал 42)
   ```

2. **Унификация.** Решаване на системата от уравнения чрез алгоритъма на
   Робинзон (Robinson, 1965):
   ```
   unify(α, i64) = {α ↦ i64}
   unify(α → β, i64 → f64) = {α ↦ i64, β ↦ f64}
   unify(α, α) = ∅
   ```

3. **Обобщение.** Свободните типови променливи, които не се срещат в Γ,
   се обобщават:
   ```
   Γ ⊢ e : σ    където σ = ∀α. α → α
   ```

Бага опростява класическия алгоритъм по два начина:

- Няма автоматично обобщение на let-свързвания (изисква явни анотации за
  полиморфни функции).
- Ефектовите анотации се извеждат *заедно* с типовете — ефектовото множество
  е част от унификационното уравнение.

**Теорема (Коректност на извеждането).** Ако алгоритъмът за извеждане върне
тип T за израз e в контекст Γ, тогава `Γ ⊢ e : T` е доказуемо по правилата
от §1.5.

## 2. Ефектови Системи

### 2.1 Алгебрични ефекти

Алгебричните ефекти (Plotkin & Power, 2003) предоставят унифицирана рамка за
странични ефекти. Ефектът се определя от:

- **Сигнатура** Σ — множество от операции `op : A → B`
- **Уравнения** — закони, на които операциите се подчиняват

Например, ефектът `IO` има операции:

```
read  : Path → String
write : Path × String → unit
```

а ефектът `NotFound` има една операция:

```
not_found : Path → ⊥
```

Обработчик (handler) на ефект е интерпретация на сигнатурата:

```
h : ∀α. (op : A → B) → (A → B) → B
```

### 2.2 Редове на ефекти

Ефектовото множество в Бага образува *ред* (row) в смисъла на Gifford &
Lucassen (1986):

```
E ::= ε                    празно множество (чисто изчисление)
    | E ∪ {e}              добавяне на ефект
```

където ε е празното множество. Редът е *идемпотентен* и *комутативен*:

```
E ∪ {e} ∪ {e} = E ∪ {e}          (идемпотентност)
E ∪ {e₁} ∪ {e₂} = E ∪ {e₂} ∪ {e₁}  (комутативност)
```

Следователно ефектовото множество е *множество* в теоретико-множествения
смисъл, а не списък.

### 2.3 Ефектов полиморфизъм

Функция, която работи с произволен ефект, се типизира с *ефектова променлива*:

```
∀E. (T₁ !E) → T₂ !E
```

Това означава: „за всяко ефектово множество E, ако входът има ефект E, то и
изходът има ефект E". Функцията *не добавя* свои ефекти — тя ги *пренася*.

Пример:

```baga
// Тази функция е ефектово-полиморфна:
// тя не знае какви ефекти има f, но ги запазва
fn приложи(f: fn(i64) -> i64 !E, x: i64) -> i64 !E {
    return f(x)
}
```

### 2.4 Ефектовата система на Бага

#### 2.4.1 Деклариране на ефекти

Ефектите се декларират в return типа на функцията:

```baga
fn прочети_файл(път: str) -> str !IO !NotFound {
    return "съдържание"
}
```

Тук `str !IO !NotFound` означава: функцията връща низ, но изчислението може
да извърши вход/изход и може да не намери файла.

#### 2.4.2 Извеждане на ефекти

Когато функция `f` с тип `T !E₁ !E₂` бъде извикана, нейните ефекти се
*добавят* към ефектовото множество на обхващащия контекст:

```
Γ ⊢ f : T → T′ !E₁ !E₂    Γ ⊢ args : T
──────────────────────────────────────────── (Call)
Γ ⊢ f(args) : T′ !E₁ !E₂
```

При композиция ефектите се *обединяват*:

```
Γ ⊢ e₁ : T₁ !E₁    Γ, x : T₁ ⊢ e₂ : T₂ !E₂
────────────────────────────────────────────────── (Seq)
Γ ⊢ let x = e₁; e₂ : T₂ !(E₁ ∪ E₂)
```

Пример:

```baga
fn обработи(път: str) -> str !IO !NotFound {
    // прочети_файл има ефекти !IO !NotFound
    // ? ги propagate-ва нагоре
    let данни = прочети_файл(път)?
    return данни
}
// Ефектово множество на обработи: {IO} ∪ {NotFound} = {IO, NotFound}
```

#### 2.4.3 Обработка на ефекти

Операторът `catch !E => handler` *премахва* ефекта E от ефектовото множество:

```
Γ ⊢ e : T !E ∪ E′    Γ ⊢ handler : T
────────────────────────────────────────── (Catch)
Γ ⊢ e catch !E => handler : T !E′
```

Пример:

```baga
fn main() {
    let резултат = прочети_файл("данни.txt")
        catch !NotFound => "празно"
        catch !IO => "грешка"
    print(резултат)
}
// След catch !NotFound: ефекти = {IO}
// След catch !IO:       ефекти = ε (чисто)
```

#### 2.4.4 Пропагиране с оператора `?`

Операторът `?` е синтактична захар за „ако ефектът се реализира, върни го
нагоре":

```
Γ ⊢ e : T !E ∪ E′
────────────────────────────────────── (Propagate)
Γ ⊢ e? : T !E ∪ E′
```

Разликата между `e` и `e?` е семантична: `e?` означава „не обработвай
ефектите тук — прехвърли ги към обхващащата функция". Без `?`, необработените
ефекти са грешка.

#### 2.4.5 Необработени ефекти

Ако в края на функция останат необработени ефекти, които не са декларирани в
return типа, компилаторът отказва програмата:

```
Γ ⊢ body : T !E    E ⊄ E_декларирано
────────────────────────────────────────── (EffectError)
ГРЕШКА: unhandled effect !E in 'f'
```

Това е *compile-time* грешка, не runtime изключение. Програмата не се
компилира.

### 2.5 Формални правила за ефектово типизиране

Пълната система от правила:

```
──────────────────────────────────────── (Pure)
Γ ⊢ v : T !ε                    (стойностите са чисти)

Γ ⊢ f : T₁ → T₂ !E_f    Γ ⊢ x : T₁ !E_x
──────────────────────────────────────────── (App-Eff)
Γ ⊢ f(x) : T₂ !(E_f ∪ E_x)

Γ ⊢ e : T !(E ∪ {eᵢ})    Γ ⊢ h : T !E_h
──────────────────────────────────────────── (Handle)
Γ ⊢ e catch !eᵢ => h : T !(E ∪ E_h)

Γ ⊢ e : T !E    E ⊆ E_декл
──────────────────────────────────────────── (Declare)
Γ ⊢ fn f(...) -> T !E_декл { e } : unit

Γ ⊢ e : T !E    E ⊄ E_декл
──────────────────────────────────────────── (Reject)
⊢ ГРЕШКА
```

### 2.6 Сравнение с други подходи

| Система | Подход | Ефектите видими ли са? |
|---|---|---|
| **Бага** | Ефектови множества върху типове | Да, в типа |
| **Koka** (Leijen, 2017) | Алгебрични ефекти + редове | Да, в типа |
| **Eff** (Pretnar, 2015) | Алгебрични ефекти + обработчици | Да, в типа |
| **OCaml 5** | Алгебрични ефекти (runtime) | Не, само runtime |
| **Rust** | `Result<T, E>` / `Option<T>` | Частично, чрез типа |
| **Java** | Checked exceptions | Да, но не се спазва |
| **Haskell** | Монади (`IO a`, `ExceptT`) | Да, в типа |

Бага е най-близо до Koka по дух, но с по-опростен синтаксис. За разлика от
Rust, където грешката е *стойност* (`Result<T, E>`), в Бага грешката е
*измерение на типа*. За разлика от Haskell, където ефектът е *монада*, в Бага
ефектът е *анотация*.

### 2.7 Математически свойства

**Теорема (Join-полурешетка).** Множеството от всички ефектови множества
`(P(Eff), ∪, ∅)` образува join-полурешетка:

- `∅` е най-малкият елемент (чисто изчисление)
- `∪` е join-операцията
- За всяко E: `E ∪ E = E` (идемпотентност)
- За всяко E₁, E₂: `E₁ ∪ E₂ = E₂ ∪ E₁` (комутативност)
- За всяко E₁, E₂, E₃: `(E₁ ∪ E₂) ∪ E₃ = E₁ ∪ (E₂ ∪ E₃)` (асоциативност)

**Следствие.** Ефектовото множество на всяка програма е *единствено определено*
— редът на композиция не влияе на крайния резултат.

**Теорема (Монотонност).** Ако `Γ ⊢ e : T !E` и `E ⊆ E′`, тогава
`Γ ⊢ e : T !E′`. По-голямо ефектово множество е по-слаба гаранция.

## 3. Теория на Спецификациите

### 3.1 Design by Contract

Концепцията за „проектиране по договор" (Design by Contract, Meyer, 1986)
въвежда три елемента:

- **Предусловие** (precondition) P — какво трябва да е вярно преди извикване
- **Постусловие** (postcondition) Q — какво се гарантира след извикване
- **Инвариант** (invariant) I — какво остава вярно през цялото изпълнение

В класическия DbC (Eiffel) тези условия се проверяват *по време на изпълнение*.
При нарушение се хвърля изключение. Това е *динамична* проверка.

### 3.2 Как спецификациите на Бага се различават

Бага прави три фундаментални промени:

**1. Спецификацията е първокласен гражданин.** Тя не е коментар, не е
анотация, не е тест. Тя е `spec` — ключова дума в езика:

```baga
spec сортирай {
    input:
        arr: [i64]
    output: [i64]
    guarantees:
        - output is sorted
        - output has same elements as input
}
```

**2. Компилаторът е съдията.** Проверката не е по време на изпълнение, а по
време на *компилация*. Ако имплементацията нарушава гаранция, компилаторът
отказва програмата:

```
error: implementation violates specification 'сортирай':
  guarantee 'output is sorted' may not hold
  counterexample: arr = [3, 1, 2] → output = [3, 1, 2]
```

**3. Спецификацията е интерфейсът между човек и AI.** Човекът пише spec-а
(архитектът). AI пише имплементацията (изпълнителят). Компилаторът проверява
(съдията). Това е новият работен процес:

```
Човек → spec → AI → impl → Компилатор → ✓ или ✗
```

### 3.3 Формална семантика на спецификациите

Спецификацията `spec S { input: x̄ : T̄, output: T_r, guarantees: ḡ }` се
интерпретира като *логическа формула*:

```
⟦S⟧ = ∀x̄ : T̄. ∀r : T_r. f(x̄) = r → g₁(x̄, r) ∧ g₂(x̄, r) ∧ ... ∧ gₙ(x̄, r)
```

където:
- `x̄` са входните параметри
- `r` е резултатът
- `gᵢ` са гаранциите, изразени като предикати върху входа и изхода

За примера със сортирането:

```
⟦сортирай⟧ = ∀arr: [i64]. ∀r: [i64].
    сортирай(arr) = r →
    sorted(r) ∧ multiset(r) = multiset(arr)
```

### 3.4 Връзка с логиката на Хоар

Логиката на Хоар (Hoare, 1969) използва тройки:

```
{P} C {Q}
```

което означава: „ако преди изпълнение на команда C е вярно P, то след
изпълнението е вярно Q".

Спецификацията на Бага съответства на тройка на Хоар:

```
{true} f(x̄) {λr. g₁(x̄, r) ∧ ... ∧ gₙ(x̄, r)}
```

Предусловието е `true` (няма ограничения върху входа), а постусловието е
конюнкцията на гаранциите.

**Правило за следствие (от логиката на Хоар):**

```
{P} C {Q}    P′ ⊃ P    Q ⊃ Q′
──────────────────────────────────
{P′} C {Q′}
```

Това означава: ако спецификацията гарантира Q, то всяка по-слаба гаранция Q′
(такава че Q ⊃ Q′) също е валидна.

### 3.5 Проверка на спецификации

Компилаторът на Бага проверява спецификациите чрез:

1. **Синтактична проверка.** Спецификацията е добре образувана.
2. **Съвместимост на типовете.** Типовете в spec съвпадат с типовете на
   функцията:

```baga
// ГРЕШКА: spec казва output: f64, но функцията връща i64
spec грешна {
    input:
        x: i64
    output: f64
    guarantees:
        - something
}

fn грешна(x: i64) -> i64 {
    return x
}
```

3. **Семантична проверка.** Гаранциите са изпълними (в общия случай това е
   неразрешим проблем, затова Бага използва консервативен анализ).

**Теорема (Консервативност).** Ако компилаторът приеме програмата, то
спецификацията е удовлетворена. Обратното не е гарантирано — компилаторът
може да отхвърли коректна програма (false positive), но никога не приема
некоректна (false negative).

## 4. Извличане на Доказателства

### 4.1 Извличане на доказателства в Coq

В Coq (The Coq Development Team, 1989) доказателствата се *пишат* на езика
Gallina:

```coq
Theorem plus_comm : ∀ n m : nat, n + m = m + n.
Proof.
  intros n m.
  induction n as [| n' IHn'].
  - simpl. rewrite <- plus_n_O. reflexivity.
  - simpl. rewrite IHn'. reflexivity.
Qed.
```

Извличането (extraction) в Coq е *от доказателство към програма* — програмата
се получава като страничен продукт от доказателството.

### 4.2 Подходът на Бага: обратната посока

Бага прави обратното: от *програма* към *proof sketch*. Компилаторът анализира
кода и *извлича* четими теореми:

```
$ ./baga --proofs examples/faktorial.baga

proofs for факториел:
  theorem факториел_signature:
    ∀ n: i64. факториел(n) → i64

  theorem факториел_terminates:
    ∀ n: i64. terminates(факториел(n))
    evidence: base case with early return, 2 return paths

  theorem факториел_pure:
    факториел is pure (no declared effects)
```

Това не са формални доказателства в смисъла на Coq или Lean. Те са
*скици* (sketches) — твърдения, които човек (или AI) може да прочете,
разбере и верифицира.

### 4.3 Какво се извлича

Бага извлича три класа теореми:

#### 4.3.1 Сигнатурни теореми

За всяка функция `f` с параметри `x̄ : T̄` и return тип `T_r`:

```
theorem f_signature:
    ∀ x̄ : T̄. f(x̄) → T_r
```

Това е тривиално вярно — то е просто типът на функцията, преформулиран като
теорема. Но то е *четимо* и служи като документация.

#### 4.3.2 Теореми за терминация

За всяка функция компилаторът анализира дали тя завършва:

```
theorem f_terminates:
    ∀ x̄. terminates(f(x̄))
    evidence: ...
```

Анализът включва:
- Наличие на базов случай (early return)
- Намаляващ аргумент при рекурсия
- Краен брой пътища за връщане

Пример:

```baga
fn факториел(n: i64) -> i64 {
    if n <= 1 {
        return 1          // базов случай
    }
    return n * факториел(n - 1)  // n намалява
}
```

Компилаторът вижда: при `n <= 1` има директно връщане; при `n > 1`
рекурсивното извикване е с `n - 1 < n`. Следователно функцията терминация.

#### 4.3.3 Теореми за чистота

Ако функцията няма декларирани ефекти:

```
theorem f_pure:
    f is pure (no declared effects)
```

Това означава: `f` не извършва IO, не хвърля грешки, не модифицира външно
състояние. Тя е *детерминирана* функция в математическия смисъл.

### 4.4 Връзка с други системи

| Система | Посока | Формалност |
|---|---|---|
| **Coq** | Доказателство → Програма | Пълна (machine-checked) |
| **Lean 4** | Доказателство → Програма | Пълна (machine-checked) |
| **Dafny** | Спецификация → Проверка | Частична (SMT solver) |
| **Бага** | Програма → Proof sketch | Скица (human-readable) |

Бага не се конкурира с Coq или Lean. Тя заема различна ниша: *автоматична
генерация на четими твърдения*, които служат като мост между кода и формалната
верификация.

### 4.5 Работен процес за AI верификация

Пълният цикъл:

```
1. Човекът пише спецификация:
   spec сортирай {
       input: arr: [i64]
       output: [i64]
       guarantees:
           - output is sorted
           - output has same elements as input
   }

2. AI генерира имплементация:
   fn сортирай(arr: [i64]) -> [i64] { ... }

3. Компилаторът проверява spec ↔ impl

4. Компилаторът извлича proof sketches:
   theorem сортирай_preserves_elements:
       ∀ arr arr'. сортирай(arr) = arr' → multiset(arr) = multiset(arr')
   theorem сортирай_produces_sorted:
       ∀ arr arr'. сортирай(arr) = arr' → sorted(arr')
   theorem сортирай_terminates:
       ∀ arr. terminates(сортирай(arr))

5. Човекът (или друг AI) верифицира proof sketches
```

Това е *gradual verification* — не е нужно всичко да е доказано формално.
Достатъчно е да е *четимо* и *проверимо*.

## 5. Self-Hosting и Bootstrapping

### 5.1 Проблемът с bootstrap-а

Всеки компилатор е програма. Но програмите се компилират от компилатор.
Възниква въпросът: кой компилира първия компилатор?

Това е проблемът за *bootstrap-а* — аналог на проблема за кокошката и яйцето.
Решението е *bootstrapping*: написване на минимален компилатор на друг език
(обикновено C), който може да компилира пълния компилатор на самия език.

### 5.2 Ритуалът на Бага

Бага следва класическия ритуал с три стъпки:

```
Стъпка 1: C компилатор (bootstrap)
    gcc → baga₁ (двоичен файл)

Стъпка 2: baga₁ компилира compiler.baga
    baga₁ → C код → gcc → baga₂

Стъпка 3: baga₂ компилира compiler.baga
    baga₂ → C код → gcc → baga₃

Проверка: baga₂ == baga₃ ?
    Ако да → компилаторът е коректен (с висока вероятност)
    Ако не → има грешка в compiler.baga или в C bootstrap-а
```

Формално, нека `C` е функцията „компилиране на Бага код към двоичен файл":

```
baga₁ = C_bootstrap(compiler.baga)
baga₂ = C(baga₁, compiler.baga)
baga₃ = C(baga₂, compiler.baga)
```

Проверката е: `baga₂ ≡ baga₃` (побитово съвпадение).

### 5.3 Теорема за неподвижната точка

Ритуалът работи благодарение на *теоремата за неподвижната точка*
(Kleene, 1952):

**Теорема.** Нека `F` е изчислима функция върху програми. Тогава съществува
програма `p` такава, че `F(p) ≡ p`.

В контекста на Бага: нека `F(x) = C(x, compiler.baga)`. Ако `baga₂` е
неподвижна точка на `F`, тогава `F(baga₂) = baga₃ = baga₂`. Проверката
`baga₂ == baga₃` е проверка за неподвижна точка.

Това не е *доказателство* за коректност — възможно е две грешки да се
компенсират. Но е изключително силен *емпиричен* тест. Вероятността за
случайно съвпадение при грешен компилатор е пренебрежимо малка.

### 5.4 Self-hosting-ът на Бага

Компилаторът на Бага, написан на Бага, се състои от три файла:

```
self/
├── lexer.baga      (234 реда)
├── parser.baga     (457 реда)
└── compiler.baga   (963 реда)
                    ─────────
                    1654 реда общо
```

Основният файл `compiler.baga` е ~960 реда. Това е възможно благодарение на:

- Липса на зависимости (няма външни библиотеки)
- Транспилиране към C (не е нужна собствена кодогенерация към машинен код)
- Опростена типова система (без generics, без traits)
- Една цел: коректност, не производителност

Философията: *багатурът се бие сам*. Компилаторът не зависи от LLVM, от
Cranelift, от външна библиотека. Само `gcc` — инструмент, който е на всяка
машина от 1987 година насам.

## 6. Математически Основи (Обобщение)

### 6.1 Теория на категориите: ефекти като монади

В теорията на категориите (Mac Lane, 1971) страничните ефекти се моделират
чрез *монади* (Moggi, 1991):

**Определение.** Монада върху категория C е тройка `(T, η, μ)`, където:
- `T : C → C` е ендоморфизъм (функтор от C в C)
- `η : Id → T` е единица (return)
- `μ : T² → T` е умножение (join/flatten)

удовлетворяващи законите:

```
μ ∘ Tη = id          (ляв идентитет)
μ ∘ ηT = id          (десен идентитет)
μ ∘ Tμ = μ ∘ μT      (асоциативност)
```

В Бага ефектовата анотация `T !E` съответства на монадния тип `T_E`:

```
str !IO  ≅  IO(str)     в Haskell
str !IO  ≅  T_IO(str)   в Бага
```

Разликата е прагматична: в Haskell монадата е *тип*, в Бага е *анотация*.
Математическата структура е една и съща.

**Композиция на монади.** Ако `T₁` и `T₂` са монади, тяхната композиция
`T₁ ∘ T₂` не е непременно монада. Това е известният проблем с композицията
на монади. Бага го решава прагматично: ефектовите множества се *обединяват*,
а не се композират. Това е по-слабо, но по-практично.

### 6.2 Теория на решетките: ефектови множества

**Определение.** Полурешетка (join-semilattice) е наредена двойка `(L, ∨)`,
където `∨ : L × L → L` е:
- идемпотентна: `a ∨ a = a`
- комутативна: `a ∨ b = b ∨ a`
- асоциативна: `(a ∨ b) ∨ c = a ∨ (b ∨ c)`

**Теорема.** Множеството от всички ефектови множества `(P(Eff), ∪)` с
операция обединение образува join-полурешетка с най-малък елемент `∅`.

**Доказателство.** Обединението на множества е идемпотентно, комутативно и
асоциативно. Празното множество `∅` е неутрален елемент: `E ∪ ∅ = E`.
Наредбата е включване на множества: `E₁ ≤ E₂ ⟺ E₁ ⊆ E₂`. ∎

**Следствие.** За всяка програма p на Бага съществува *единствено* минимално
ефектово множество `eff(p)`, което се изчислява чрез:

```
eff(v) = ∅                              (стойност)
eff(f(x)) = eff(f) ∪ eff(x)            (извикване)
eff(let x = e₁; e₂) = eff(e₁) ∪ eff(e₂)  (последователност)
eff(e catch !E => h) = eff(e) \ {E} ∪ eff(h)  (обработка)
```

### 6.3 Логика: съответствие на Къри-Хауард-Ламбек

Класическото съответствие на Къри-Хауард се разширява от Ламбек (Lambek, 1980)
до *тристранно* съответствие:

```
Програми  ←→  Доказателства  ←→  Морфизми в категория
```

| Бага | Логика | Категории |
|---|---|---|
| Тип `T` | Предложение | Обект |
| Програма `t : T` | Доказателство | Морфизъм `1 → T` |
| Функция `f : A → B` | Импликация `A ⊃ B` | Морфизъм `A → B` |
| Композиция `g ∘ f` | Modus ponens | Композиция на морфизми |
| Ефект `!E` | Модален оператор `◇_E` | Монада `T_E` |
| Spec | Аксиома | Универсално свойство |

Това тристранно съответствие дава на Бага три *езика* за описание на една и
съща структура:

1. **Програмен** — кодът, който пишем
2. **Логически** — теоремите, които доказваме
3. **Категорен** — структурата, която описваме

### 6.4 Теория на неподвижната точка

**Теорема на Клийн (Kleene, 1952).** За всяка изчислима функция
`f : ℕ → ℕ` съществува `n` такова, че `φ_n = φ_{f(n)}`, където `φ_i` е
i-тата частична изчислима функция.

**Теорема на Тарски (Tarski, 1955).** Нека `(L, ≤)` е пълна решетка и
`f : L → L` е монотонна функция. Тогава множеството от неподвижни точки на f
образува пълна решетка. По-специално, съществува най-малка неподвижна точка:

```
lfp(f) = ⋂ {x ∈ L | f(x) ≤ x}
```

**Приложение в Бага.** Рекурсивните функции се интерпретират чрез най-малката
неподвижна точка на функционала:

```baga
fn факториел(n: i64) -> i64 {
    if n <= 1 { return 1 }
    return n * факториел(n - 1)
}
```

Дефинираме функционал `F`:

```
F(g)(n) = if n ≤ 1 then 1 else n · g(n - 1)
```

Тогава `факториел = lfp(F)` — най-малката неподвижна точка на F.
Теоремата за терминация (§4.3.2) е еквивалентна на твърдението, че
итерацията `F⁰(⊥) ⊑ F¹(⊥) ⊑ F²(⊥) ⊑ ...` достига неподвижна точка
за краен брой стъпки за всеки вход.

## Заключение

Бага не изобретява нова математика. Тя *рекомбинира* съществуващи теории:

- Просто типизирано ламбда смятане (Church, 1940)
- Ефектови системи (Gifford & Lucassen, 1986; Plotkin & Power, 2003)
- Design by Contract (Meyer, 1986)
- Логика на Хоар (Hoare, 1969)
- Съответствие на Къри-Хауард (Curry, 1934; Howard, 1980)
- Монади (Moggi, 1991)
- Теорема за неподвижната точка (Kleene, 1952)

Въпросът не е „кое е ново". Въпросът е „кое не е било залепено заедно".

Линейната логика е от 1987. Отне 30 години да стане Rust.
Ефектовите системи са от 2003. Може би сега е моментът.
