# Архитектура на Компилатора на Бага

## Общ преглед

Бага е статично типизиран език за програмиране с поддръжка на кирилски
идентификатори, компилационна проверка на ефекти и верификация на спецификации.
Компилаторът е **C транспилер** — генерира C код, който след това се компилира
с gcc до нативен изпълним файл.

Проектът съдържа две реализации на компилатора:

1. **C Bootstrap компилатор** (~13k реда C в `src/`, вкл. `verify.c`) — пълната референтна имплементация
2. **Self-Hosted компилатор** (~2660 реда Бага в `self/compiler.baga`, плюс lexer/parser) — fixed-point самокомпилация (`baga2 == baga3`)

## C Bootstrap Компилатор

### Модулна структура

| Файл | Редове | Отговорност |
|------|--------|-------------|
| `src/lexer.c` | ~400 | Токенизация, UTF-8 обработка |
| `src/parser.c` | ~900 | Рекурсивно спускане → AST |
| `src/checker.c` | ~790 | Извеждане на типове, проверка на ефекти, спецификации |
| `src/codegen_c.c` | ~840 | C транспилация с кодиране на имена |
| `src/proofs.c` | ~164 | Извличане на доказателствени скици |
| `src/main.c` | ~212 | CLI интерфейс, оркестрация на конвейера |
| `include/baga.h` | ~460 | Споделени структури от данни и декларации |

### CLI интерфейс

```
baga [опции] <файл.baga>

Опции:
  --emit-c    Генерирай C код на stdout (без компилация)
  --check, --lib  Само parse + typecheck (без main, без codegen) — за библиотеки
  --test-specs  Property-based тестване на spec договорите
  --verify    Статична верификация на requires/ensures
  --json      Машинно-четим JSON изход (с --verify)
  --ast       Изпечатвай AST (debug)
  --tokens    Изпечатвай потока от токени (debug)
  --specs     Изпечатвай извлечените спецификации
  --proofs    Изпечатвай доказателствените скици
  -I <dir>    Директория за търсене на import (повтаряем)
  --version, -V  Версия на компилатора
```

По подразбиране: генерира C → компилира с `gcc -O2` → изпълнява → почиства.

Пакетите (`sandak.toml` манифести, lock, git зависимости) се управляват от
отделния инструмент **sandak** (`src/sandak.c`), който изчислява `-I`
флаговете и вика компилатора — виж README, „Packages — sandak".

### Фаза 1: Лексер (`src/lexer.c`)

Лексерът преобразува суровите байтове на изходния код в поток от токени.

**Ключови характеристики:**
- UTF-8 съвместимост: кирилски символи (U+0400–U+04FF) са валидни в идентификатори
- Разпознаване на двусимволни оператори: `->`, `==`, `!=`, `<=`, `>=`, `&&`, `||`, `..`, `=>`
- Обработка на escape последователности в низове: `\n`, `\t`, `\\`, `\"`
- Проследяване на ред/колона за съобщения за грешки
- Еднократно преминаване, без връщане назад

**Структура на токен:**
```c
typedef struct {
    TokenKind kind;
    SrcPos    pos;        // {ред, колона}
    char     *text;       // лексема (в heap)
    int64_t   int_val;    // за TOK_INT_LIT
    double    float_val;  // за TOK_FLOAT_LIT
} Token;
```

**Алгоритъм:** Линейно сканиране с машина на състоянията. Всяко извикване на
`lexer_next()` връща един токен. Лексерът поглежда един символ напред за
двусимволни оператори. Идентификаторите поглъщат всеки байт ≥ 128 (UTF-8
продължаващи/водещи байтове) като част от името.

### Фаза 2: Парсер (`src/parser.c`)

Парсер с рекурсивно спускане, който изгражда дърво от `Node` структури.

**Приоритет на граматиката (нисък → висок):**
1. `||` (логическо или)
2. `&&` (логическо и)
3. `==`, `!=`, `<`, `>`, `<=`, `>=` (сравнение)
4. `+`, `-` (събиране/изваждане)
5. `*`, `/`, `%` (умножение/деление)
6. Унарни: `-`, `!`, `&`, `*`
7. Примитиви: литерали, идентификатори, извиквания, скобирани изрази

**Структура на AST възел:**
```c
struct Node {
    NodeKind kind;
    SrcPos   pos;
    Type    *type;      // изведен тип (зададен от checker-а)
    union {
        int64_t int_val;                    // NODE_INT_LIT
        char *str_val;                      // NODE_STR_LIT
        char *name;                         // NODE_IDENT
        struct { BinOp bin_op; Node *left; Node *right; };  // NODE_BINARY
        struct { Node *callee; NodeVec args; };             // NODE_CALL
        struct { Node *cond; Node *then_br; Node *else_br; }; // NODE_IF
        struct { NodeVec stmts; };          // NODE_BLOCK
        struct { char *fn_name; NodeVec params; Node *ret_type; Node *fn_body; }; // NODE_FN
        // ... още 20+ варианта
    };
};
```

Подходът с маркирано обединение (tagged union) държи възлите компактни — една
алокация на възел — при поддръжка на 30+ вида възли. `NodeVec` е разширяем
масив чрез макрото `VEC(Node *)`.

### Фаза 3: Проверка (`src/checker.c`)

Извършва три анализа върху AST:

**1. Извеждане на типове (в стил Хиндли-Милнер)**
- Възходящо разпространение на типове през изразите
- Връщаните типове на функциите се извеждат от `return` твърденията
- Унификация с възстановяване от грешки (`TYPE_ERROR` потиска каскадни грешки)
- Равенство на типове: структурно за примитиви, номинално за структури

**2. Проверка на ефекти**
- Ефектите са анотации върху типовите сигнатури: `fn чети() -> str !IO`
- Разпространение: извикване на ефектна функция замърсява извикващия
- `catch !E => handler` премахва ефекта E от типа на израза
- Ефектите са само компилационни — изтриват се при генериране на код

**3. Верификация на спецификации**
- `spec` блоковете декларират входни/изходни типове и гаранции
- Проверката потвърждава, че сигнатурата на функцията съответства на spec-а
- Гаранциите се извличат, но не се доказват формално (за човешки/AI одит)

**Типова система:**
```c
typedef enum {
    TYPE_VOID, TYPE_BOOL, TYPE_I32, TYPE_I64, TYPE_F64,
    TYPE_STR, TYPE_ARRAY, TYPE_REF, TYPE_STRUCT, TYPE_FN,
    TYPE_VEC, TYPE_ERROR
} TypeKind;

struct Type {
    TypeKind kind;
    Type *elem;         // елемент на TYPE_ARRAY
    Type *pointee;      // цел на TYPE_REF
    char *name;         // име на TYPE_STRUCT / TYPE_FN
    Type *ret;          // върнат тип на TYPE_FN
    Type **params;      // параметри на TYPE_FN
    int nparams;
    char **effects;     // анотации за ефекти
    int n_effects;
};
```

### Фаза 4: Генериране на код (`src/codegen_c.c`)

Транспилира типизираното AST в C99 код.

**Кодиране на имена (name mangling):**
Всички потребителски имена получават префикс `b_`. Не-ASCII байтовете се
кодират като `_XX` (шестнадесетично):
```
факториел → b__d1__84__d0__b0__d0__ba__d1__82__d0__be__d1__80__d0__b8__d0__b5__d0__bb
main      → b_main
```

Това гарантира, че кирилските идентификатори стават валидни C символи без колизии.

**Съответствие на типовете:**
| Бага | C |
|------|---|
| `i32` | `int32_t` |
| `i64` | `int64_t` |
| `f64` | `double` |
| `bool` | `int` |
| `str` | `const char *` |
| `Vec` | `baga_Vec *` |
| `void` | `void` |
| `&T` | `T *` |
| `[T] | `T *` |

**Вектор (Vec):**
```c
typedef struct { void **data; int64_t len; int64_t cap; } baga_Vec;
```
Динамичен масив с изтрит тип. Отделни варианти push/get/set за `i64` и `str`
осигуряват типова безопасност на ниво Бага, споделяйки една C имплементация.

**Неявен return:**
Ако последният оператор във функция с нев void тип е израз, codegen-ът го
преобразува в `return expr;`.

---

### Фаза 5: Извличане на доказателства (`src/proofs.c`)

Пас след парсване, който обхожда AST-то и генерира четими доказателствени скици:
- Сигнатури на функции с ефекти
- Откриване на базов случай (if-с-return модел)
- Откриване на рекурсия (евристика)
- Гаранции от спецификации, изброени като аксиоми

Не са формални доказателства — структурирана документация за човешка или AI верификация.

### LLVM Backend (`src/codegen_llvm.c`)

Алтернативен backend, който генерира LLVM IR директно от AST-то
(`make llvm` → `baga-llvm --emit-llvm файл.baga`; изисква LLVM 14).

Поддържа целия езиков набор от примерите:
- Типове: `i64`, `i32`, `f64`, `bool`, `str`, `void`, `Vec`, потребителски
  struct-ове (by value, както в C backend-а)
- Изрази: литерали, ident, binary (int + f64 с промоция i64→f64 като в C
  backend-а), unary (`-`, `!`), повиквания
- Оператори: let, присвояване (`=`, `+=` …), return, if/else, while,
  for (`0..n`) с break/continue, match върху i64, enum варианти
- `print`/`println`/`write` — изходът е байт за байт същият като C backend-а
  (`%lld`, `%g`, `true`/`false`, `%s`)
- Str/io builtin-и: `len`, `char_at`, `substr`, `concat`, `str_eq`, `chr`,
  `ord`, `read_file` — lazy IR функции (`baga_rt`), огледало на C preamble-а
- Vec builtin-и: `vec_new`, `vec_push`, `vec_get`, `vec_set`, `vec_push_str`,
  `vec_get_str`, `vec_set_str`, `vec_len` — `baga_Vec` като named struct в IR,
  със същия `(void*)(intptr_t)x` трик като C (`inttoptr`/`ptrtoint`)
- Ефекти: `?` и `catch` са compile-time тагове — pass-through, както в codegen_c
- Contracts: wrapper pattern като C backend-а — requires преди и ensures след
  повикването; нарушение → същото съобщение на stderr + exit(1)
  (редът `  вход:` е само за C/`--test-specs`)

Принцип „никакви тихи стойности": всеки конструкт извън този списък
(масиви `[T]`, референции `&`/`*`, match върху не-i64, str `==` в binary
израз, присвояване на поле/индекс) е compile-time грешка, а не мълчаливо
грешен код:

```
baga: LLVM backend: неподдържан конструкт '<какво>'
```

Оракълът `tests/llvm_oracle.sh` (викан от `make test`) сравнява изхода и
exit кода на C backend-а и LLVM backend-а (през `lli-14`) за всички примери
— 14/14 OK.

## Self-Hosted Компилатор (`self/compiler.baga`)

### Архитектура

Self-hosted компилаторът обединява лексер + парсер + codegen в един файл от 964
реда на Бага. Умишлено пропуска checker-а (без извеждане на типове) и използва
по-просто представяне на AST.

**Плоско AST (свързан списък):**
Вместо дърво от heap-алокирани структури, self-hosted компилаторът използва
четири успоредни вектора:

```
nk: Vec  — вид на възела (i64)
nt: Vec  — текст на възела (str)
fc: Vec  — индекс на първо дете (i64, -1 = няма)
ns: Vec  — индекс на следващ брат (i64, -1 = няма)
```

Децата образуват едносвързан списък: `first_child` сочи към главата,
`next_sibling` свързва братята. Това избягва рекурсивни структури от данни и
работи в рамките на ограничената типова система на Бага (без структури, без
изброими типове — само Vec).

**Видове възли:**
| ID | Вид | Описание |
|----|-----|----------|
| 0 | INT | Целочислен литерал |
| 1 | STR | Низов литерал |
| 2 | IDENT | Идентификатор |
| 3 | BINARY | Бинарна операция (текст = оператор) |
| 4 | CALL | Извикване на функция |
| 5 | BLOCK | Блок от оператори |
| 6 | LET | Свързване на променлива |
| 7 | RETURN | Оператор return |
| 8 | IF | Условно разклонение |
| 9 | WHILE | Цикъл while |
| 10 | EXPR_STMT | Израз като оператор |
| 11 | FN | Дефиниция на функция |
| 12 | PARAM | Параметър (текст = "име:тип") |
| 13 | PROGRAM | Коренов възел |
| 14 | BREAK | Оператор break |
| 15 | CONTINUE | Оператор continue |
| 16 | TYPE | Анотация за върнат тип |
| 17 | ASSIGN | Присвояване |
| 18 | FOR | Цикъл for (диапазонен) |

### Вградени функции (17)

| Име в Бага | C функция | Сигнатура |
|------------|-----------|-----------|
| `len` | `baga_len` | `str → i64` |
| `char_at` | `baga_char_at` | `(str, i64) → i64` |
| `substr` | `baga_substr` | `(str, i64, i64) → str` |
| `concat` | `baga_concat` | `(str, str) → str` |
| `str_eq` | `baga_str_eq` | `(str, str) → i64` |
| `chr` | `baga_chr` | `i64 → str` |
| `ord` | `baga_ord` | `str → i64` |
| `read_file` | `baga_read_file` | `str → str` |
| `write` | `baga_write` | `str → void` |
| `vec_new` | `baga_vec_new` | `() → Vec` |
| `vec_push` | `baga_vec_push_i64` | `(Vec, i64) → void` |
| `vec_push_str` | `baga_vec_push_str` | `(Vec, str) → void` |
| `vec_get` | `baga_vec_get_i64` | `(Vec, i64) → i64` |
| `vec_get_str` | `baga_vec_get_str` | `(Vec, i64) → str` |
| `vec_set` | `baga_vec_set_i64` | `(Vec, i64, i64) → void` |
| `vec_set_str` | `baga_vec_set_str` | `(Vec, i64, str) → void` |
| `vec_len` | `baga_vec_len` | `Vec → i64` |

### Типово-съобразен Codegen

Self-hosted компилаторът извежда C типове евристично:
- Низови литерали → `const char *`
- Извиквания на `concat`, `substr`, `chr`, `read_file` → `const char *`
- Извиквания на `vec_new` → `baga_Vec *`
- Извиквания на потребителски функции → търси анотацията за върнат тип
- Всичко останало → `int64_t`

### Предварителни декларации

Всички функции се издават като C прототипи първо, след това следват дефинициите.
Това позволява взаимна рекурсия без топологично сортиране.

## Обосновка на дизайнерските решения

### Защо C транспилация (а не LLVM/Cranelift)?

1. **Простота**: ~840 реда codegen срещу хиляди за същински backend
2. **Преносимост**: gcc/clang са налични навсякъде
3. **Отладка**: генерираният C код е четим от човек
4. **Оптимизация**: gcc -O2 осигурява продукционно качество безплатно
5. **Bootstrapping**: C компилаторът може да се компилира само с gcc

### Защо плоско AST в Self-Hosted версията?

Бага (Фаза 1) няма:
- Структури с типизирани полета (в self-hosted подмножеството)
- Изброими типове
- Рекурсивни типове от данни
- Генерици

Подходът свързан-списък-във-вектори работи в тези ограничения, като същевременно
е ефективен (O(1) създаване на възел, O(деца) обхождане).

### Защо ефектите са (почти) само компилационни?

Ефектите без payload (`!IO`, `!Error`) служат като документация и статични
гаранции. Те се изтриват при генериране на код, защото:
- C няма концепция за ефекти
- Типовата система налага дисциплина на ефектите по време на компилация

От M20 насетне ефектите с payload (`!E(T)`) имат runtime модел: thread-local
`baga_eff` слот и raise/try/catch lowering и в двата backend-а. Само
payload-less ефектите остават чиста compile-time фикция без цена.

### Защо десетично кодиране в Self-Hosted mangling-а?

C bootstrap-ът използва шестнадесетично (`_%02x`), но self-hosted компилаторът
използва десетично (`int_to_str(c)`), защото Бага няма примитив за шестнадесетично
форматиране. И двата подхода пораждат уникални, безконфликтни кодирания — просто
не генерират идентични C символи. Това е приемливо, защото self-hosted
компилаторът е отделен изпълним файл.

## Анализ на грешки (Self-Hosting)

### Грешка 1: Escape последователностите не се преобразуват

**Симптом:** Низове съдържащи `\n` отпечатваха буквално обратно наклонена черта
и n вместо нов ред.

**Причина:** Токенизаторът съхраняваше суровите символи от източника без
обработка на escape последователности. `\n` оставаше като два символа (92, 110)
вместо един (10).

**Поправка:** Добавена обработка на escape-ове в клона за низови литерали на
`tokenize()`:
```
if sc == 92 {
    pos = pos + 1
    let ec = char_at(src, pos)
    if ec == 110 { sval = concat(sval, chr(10)) }  // \n
    if ec == 116 { sval = concat(sval, chr(9)) }   // \t
    if ec == 92  { sval = concat(sval, chr(92)) }  // \\
    if ec == 34  { sval = concat(sval, chr(34)) }  // \"
}
```

### Грешка 2: Липсващ неявен return

**Симптом:** Функции, чийто последен оператор е израз, връщаха боклук.

**Причина:** Codegen-ът издаваше последния израз като оператор (`expr;`) вместо
`return expr;`. C функциите излизат от тялото без връщане на стойност —
неопределено поведение.

**Поправка:** В `emit_fn_def`, когато последният оператор във функция с нев void
тип е EXPR_STMT (вид 10), се издава `return <expr>;` вместо обикновен израз.

### Грешка 3: Предварителните декларации не се обработват

**Симптом:** Парсерът блокираше при среща на `fn foo() -> i64` без тяло.

**Причина:** Парсерът безусловно очакваше `{` след върнатия тип. Предварителните
декларации (само прототип, без тяло) са необходими за взаимна рекурсия.

**Поправка:** След парсване на върнатия тип, проверява се дали следващият токен е
`{`. Ако не — FN възелът се връща без BLOCK дете. Codegen-ът пропуска функциите
без тяло при издаване на дефинициите (те вече са издадени като прототипи).

### Грешка 4: Void върнат тип се подразбираше като int64_t

**Симптом:** Void функции се генерираха като `int64_t f(void)` — gcc предупреждения
за липсващи return оператори.

**Причина:** `fn_ret_c_type()` връщаше `"int64_t"` по подразбиране, когато не
намери TYPE дете. Функции без явен `-> тип` трябва да са `void`.

**Поправка:** Променен върнатият тип по подразбиране в `emit_fn`/`emit_fn_def` на
`"void"`, когато сред децата на функцията няма TYPE възел (вид 16).

## Характеристки на производителност

### Скорост на компилация

| Фаза | Сложност | Тясно място |
|------|----------|-------------|
| Лексер | O(n) | Едно преминаване, без алокация на символ |
| Парсер | O(n) | Рекурсивно спускане, един възел на токен |
| Проверка | O(n · d) | d = макс. дълбочина на влагане |
| Codegen | O(n) | Линейно обхождане на AST, fprintf към файл |
| gcc | O(n²) най-лошо | Доминира общото време за компилация |

За типични програми (< 10 000 реда), фазите на Бага завършват за < 50 ms.
Компилацията с gcc отнема 200–500 ms в зависимост от нивото на оптимизация.

### Памет

- C bootstrap: аренен стил (един `malloc` на възел, освобождаване при изход)
- Self-hosted: разширяване на Vec (стратегия за удвояване), без освобождаване
- Пикова памет: ~2× размера на източника за AST + поток от токени

### Качество на генерирания код

Тъй като изходът минава през `gcc -O2`:
- Опашкови извиквания се оптимизират където е приложимо
- Развиване на цикли, векторизация — наследени от gcc
- Низовите операции са наивни (malloc при всяко concat) — без интерниране или rope
- Vec използва `void**` — без специализация, индирекция на всеки достъп

### Производителност на Self-Hosted компилатора

Self-hosted компилаторът е ~5–10× по-бавен от C bootstrap-а поради:
- Конкатенация на низове за издаване на код (O(n²) спрямо размера на изхода)
- Без хеш таблици (линейно търсене за вградени функции, резолюция на имена)
- Vec-базираното AST има по-лоша кеш локалност от структурно-базираното

Това е приемливо: целта на self-hosted компилатора е доказателство за коректност,
не продукционна употреба.

CC      ?= gcc

LDFLAGS := -lm
SRCS    := src/main.c src/lexer.c src/parser.c src/checker.c src/codegen_c.c src/proofs.c

## Бъдещи направления

- Инкрементална компилация (пропускане на непроменени модули)
- Собствен JIT backend (отделен проект) за REPL; LLVM backend-ът вече покрива нативната генерация
- Пълни алгебрични ефекти (first-class хендлъри, континуации) — payload
  ефектите (M20) вече имат runtime raise/catch
- Формална верификация на доказателства (интеграция с Lean/Coq)
- Стандартна библиотека отвъд 17-те вградени функции

Генеричните типове и trait системата са реализирани в M21–M24
(мономорфизация, статичен dispatch).
