# Baga: Theory and Mathematical Foundations

> *Nothing is new. But nothing is timely. Linear logic is from 1987. It took 30 years to become Rust. Effect systems are from 2003. Fourier–Motzkin is from 1826/1936. Maybe now is the time.*

This document presents the formal mathematical foundations underlying the Baga programming language. Baga is built on three pillars — spec-first verification, effects as type dimensions, and automatic proof extraction — each of which draws on deep results from type theory, algebra, real geometry of polyhedra, and program logic. We develop the theory from first principles, connecting Baga's concrete syntax to the abstract mathematics that gives it meaning.

**Fair warning.** Ordinary undergraduate software-engineering programmes teach syntax, OOP, and HTTP. They do **not** teach join-semilattices of effect rows, Hoare triples with decreases measures, Fourier–Motzkin elimination over ℚ, Farkas certificates, the ℤ/ℚ gap for strict inequalities, or sound axiom envelopes for nonlinear products. This document does. Read it as the mathematical spine of the compiler, not as a tutorial.

## 1. Type Theory Foundations

### 1.1 Simply Typed Lambda Calculus

The simply typed lambda calculus (STLC) provides the minimal core from which Baga's type system extends. We recall its structure.

**Types.** The set of simple types is generated by the grammar:

    T ::= B | T → T

where B ranges over base types (integers, booleans, strings).

**Terms.** Raw terms are generated by:

    t ::= x | λx: T. t | t₁ t₂

where x ranges over variables, λx: T. t is abstraction, and t₁ t₂ is application.

**Typing judgments.** A typing judgment has the form:

    Γ ⊢ t : T

read "in context Γ, term t has type T." The context Γ is a finite mapping from variables to types: Γ = x₁: T₁, x₂: T₂, ..., xₙ: Tₙ.

The typing rules are:

    -------- (Var)          Γ, x: T ⊢ t : T'
    Γ ⊢ x : T               ------------------- (Abs)
    (if x: T ∈ Γ)           Γ ⊢ λx: T. t : T → T'

    Γ ⊢ t₁ : T → T'    Γ ⊢ t₂ : T
    --------------------------------- (App)
    Γ ⊢ t₁ t₂ : T'

**Theorem (Subject Reduction / Type Safety).** If Γ ⊢ t : T and t → t' (t reduces to t'), then Γ ⊢ t' : T.

**Theorem (Strong Normalization).** Every well-typed term in STLC terminates.

These two properties — safety and termination — are inherited by Baga's core calculus and extended with effects and specifications.

### 1.2 The Curry-Howard Correspondence

The Curry-Howard correspondence (also called the proofs-as-programs interpretation) establishes an isomorphism between:

| Logic | Type Theory | Baga |
|-------|-------------|------|
| Proposition | Type | `T` |
| Proof of P | Program of type P | `fn f(...) -> T { ... }` |
| Implication P → Q | Function type P → Q | `fn(x: P) -> Q` |
| Conjunction P ∧ Q | Product type (P, Q) | `struct { a: P, b: Q }` |
| Disjunction P ∨ Q | Sum type | `enum` / `match` |
| Truth ⊤ | Unit type | `()` |
| Falsehood ⊥ | Empty type | (uninhabited) |
| ∀x. P(x) | Dependent product | spec guarantees |

Under this correspondence, a Baga function:

```baga
fn факториел(n: i64) -> i64 {
    if n <= 1 {
        return 1
    }
    return n * факториел(n - 1)
}
```

is simultaneously:
- A **program** computing the factorial function.
- A **proof** of the proposition "for all n: i64, there exists an i64 result."
- A **witness** that the type `i64 → i64` is inhabited.

### 1.3 Baga's Type System: Extension with Effects

Baga extends the STLC with **effect annotations**. The type grammar becomes:

    T ::= i64 | f64 | str | bool | [T] | &T | Vec | T !E₁ ... !Eₙ

where:
- `i64` — 64-bit signed integers
- `f64` — 64-bit IEEE 754 floating-point
- `str` — UTF-8 string slices
- `bool` — boolean values (true, false)
- `[T]` — dynamic array of elements of type T
- `&T` — reference (borrow) to a value of type T
- `Vec` — opaque dynamic array handle (used in self-hosting)
- `T !E₁ ... !Eₙ` — type T with effect annotations E₁ through Eₙ

The critical insight is that **effects are part of the type**:

    str !IO !NotFound  ≠  str

These are distinct types. A function returning `str !IO !NotFound` cannot be used where a pure `str` is expected without handling the effects.

**Definition (Effect-Annotated Type).** An effect-annotated type is a pair (T, E) where T is a base type and E ⊆ 𝔼 is a finite set of effects from the effect universe 𝔼 = {!IO, !NotFound, !Permission, ...}. We write T !E₁ ... !Eₙ for (T, {E₁, ..., Eₙ}).

**Definition (Purity).** A type T with no effect annotations (E = ∅) is called **pure**. We write pure(T) ⟺ E = ∅.

### 1.4 Typing Rules for Baga Constructs

**Let binding:**

    Γ ⊢ e : T     Γ, x: T ⊢ body : T'
    ------------------------------------- (Let)
    Γ ⊢ let x = e; body : T'

For mutable bindings:

    Γ ⊢ e : T     Γ, x: mut T ⊢ body : T'
    ----------------------------------------- (LetMut)
    Γ ⊢ let mut x: T = e; body : T'

**Function definition:**

    Γ, x₁: T₁, ..., xₙ: Tₙ ⊢ body : T_ret !E
    ---------------------------------------------- (Fn)
    Γ ⊢ fn f(x₁: T₁, ..., xₙ: Tₙ) -> T_ret !E : T₁ → ... → Tₙ → T_ret !E

**Conditional:**

    Γ ⊢ cond : bool    Γ ⊢ t₁ : T !E₁    Γ ⊢ t₂ : T !E₂
    -------------------------------------------------------- (If)
    Γ ⊢ if cond { t₁ } else { t₂ } : T !(E₁ ∪ E₂)

The effect set of a conditional is the **union** of the effects of both branches.

**While loop:**

    Γ ⊢ cond : bool    Γ ⊢ body : () !E
    --------------------------------------- (While)
    Γ ⊢ while cond { body } : () !E

**Match expression:**

    Γ ⊢ scrutinee : T_s    Γ ⊢ armᵢ : T !Eᵢ  (for each arm i)
    ------------------------------------------------------------- (Match)
    Γ ⊢ match scrutinee { arm₁, ..., armₙ } : T !(E₁ ∪ ... ∪ Eₙ)

Example:

```baga
fn описание(n: i64) -> i64 {
    let резултат = match n {
        0 => 100,
        1 => 200,
        2 => 300,
        _ => 999,
    }
    return резултат
}
```

Here all arms have type `i64` with effect set ∅, so the match expression has type `i64` (pure).

### 1.5 Type Inference

Baga employs a simplified Hindley-Milner style type inference algorithm:

**Algorithm W (simplified for Baga):**

1. **Initialization.** Assign fresh type variables α₁, α₂, ... to all unannotated bindings.
2. **Constraint generation.** Walk the AST, generating equality constraints:
   - For `let x = e`: constrain typeof(x) = typeof(e)
   - For `f(args)`: constrain typeof(f) = typeof(args) → α_fresh
   - For `if cond { a } else { b }`: constrain typeof(cond) = bool, typeof(a) = typeof(b)
3. **Unification.** Solve the constraint set using Robinson unification.
4. **Effect inference.** Propagate effect sets bottom-up:
   - A call to `f: T !E` in expression position adds E to the enclosing context.
   - `catch !E₁ => handler` removes E₁ from the effect set.
   - The `?` operator propagates all effects of the operand to the enclosing function.
5. **Generalization.** At let-bindings, generalize over unconstrained type variables (restricted in Baga to monomorphic inference for simplicity).

**Theorem (Inference Soundness).** If Algorithm W assigns type T to expression e, then there exists a valid typing derivation Γ ⊢ e : T.

### 1.6 The Role of Vec

In Baga's self-hosting compiler, `Vec` serves as an opaque dynamic array type:

```baga
fn ast_kind(nk: Vec, nt: Vec, fc: Vec, ns: Vec, kind: i64, text: str) -> i64 {
    let idx = vec_len(nk)
    vec_push(nk, kind)
    vec_push_str(nt, text)
    vec_push(fc, 0 - 1)
    vec_push(ns, 0 - 1)
    idx
}
```

`Vec` is a **handle type** — it represents a mutable, heap-allocated array passed by reference. Operations on Vec (`vec_len`, `vec_push`, `vec_get`, `vec_set`) are primitive builtins. In the type theory, Vec can be modeled as:

    Vec ≅ ∃T. Ref(Array(T))

an existential type hiding the element type behind an imperative reference. In the self-hosted compiler, all Vecs are effectively `Vec<i64>` or `Vec<str>`, distinguished by the operation used (`vec_push` vs `vec_push_str`).

## 2. Effect Systems

### 2.1 Algebraic Effects: Operations and Handlers

The theory of algebraic effects, introduced by Plotkin and Power (2003), provides the mathematical foundation for Baga's effect system.

**Definition (Algebraic Effect).** An algebraic effect is specified by a set of **operations** Σ, each with an arity:

    op : A → B  (operation signature)

For Baga, the effect operations include:

    !IO         : str → str          (read/write external state)
    !NotFound   : str → str          (resource not found)
    !Permission : str → str          (access denied)

**Definition (Effect Handler).** A handler for effect E is a function:

    h : op(A) → (A → T) → T

that interprets the effect operation by providing a continuation-based semantics. In Baga syntax:

```baga
let content = read_file("data.txt")
    catch !NotFound => "empty"
    catch !IO => "error"
```

Each `catch` clause is a handler that eliminates one effect dimension by providing a fallback value.

### 2.2 Effect Rows

Following the row-polymorphism tradition (Leijen, 2017), we model effect sets as **effect rows**:

    E ::= ε | E ∪ {e} | α

where:
- ε is the empty effect row (purity)
- E ∪ {e} extends row E with effect e
- α is an effect variable (for polymorphism)

**Definition (Effect Row Equivalence).** Two effect rows are equivalent up to permutation:

    E ∪ {e₁} ∪ {e₂} ≡ E ∪ {e₂} ∪ {e₁}

This means `str !IO !NotFound` and `str !NotFound !IO` denote the same type. Effect sets are **unordered**.

### 2.3 Effect Polymorphism

A function can be polymorphic in its effects:

    ∀E. T → T !E

This denotes a function that, for any effect set E, maps T to T with effects E. In Baga, effect polymorphism is implicit — the compiler infers the most general effect set for each function.

**Example.** The identity function is effect-polymorphic:

    id : ∀E. T → T !E

but when instantiated at a specific call site, E is determined by context.

### 2.4 Baga's Effect System in Detail

**Effect declaration.** Effects are declared on return types:

```baga
fn прочети_файл(път: str) -> str !IO !NotFound {
    return "съдържание"
}
```

This declares that `прочети_файл` returns a `str` and may perform IO operations or encounter a NotFound condition.

**Effect inference.** When a function calls another function with effects, those effects propagate:

```baga
fn обработи(път: str) -> str !IO !NotFound {
    let данни = прочети_файл(път)?    // propagates !IO, !NotFound
    return данни
}
```

The `?` operator propagates all effects of the called function to the caller. Without `?`, the call would be a type error (unhandled effects in a pure context).

**Effect handling.** The `catch` construct removes effects:

```baga
fn main() {
    let резултат = прочети_файл("данни.txt")
        catch !NotFound => "празно"
        catch !IO => "грешка"
    print(резултат)    // резултат : str (pure)
}
```

After both catches, the type of `резултат` is pure `str` — all effects have been handled.

**Unhandled effects are compile-time errors.** If any effect remains unhandled:

    error: unhandled effect !IO in 'main' — declare it in the return type or catch it

This is the central safety guarantee: **no effect goes unnoticed**.

### 2.5 Formal Effect Typing Rules

We extend the typing judgment to track effects:

    Γ ⊢ e : T !E

read "in context Γ, expression e has type T with effect set E."

**Function call (effect inheritance):**

    Γ ⊢ f : T₁ → T₂ !E_f    Γ ⊢ x : T₁
    ---------------------------------------- (Call)
    Γ ⊢ f(x) : T₂ !E_f

A function call inherits the callee's effects.

**Try operator (effect propagation):**

    Γ ⊢ e : T !E    E ⊆ E_enclosing
    ----------------------------------- (Try)
    Γ ⊢ e? : T !E

The `?` operator propagates effects to the enclosing function. The side condition E ⊆ E_enclosing ensures the enclosing function declares all propagated effects.

**Catch (effect elimination):**

    Γ ⊢ e : T !(E ∪ {E₁})    Γ ⊢ h : T
    ---------------------------------------- (Catch)
    Γ ⊢ e catch !E₁ => h : T !E

Catching effect E₁ removes it from the effect set. The handler h must produce a value of the same type T.

**Sequential composition (effect union):**

    Γ ⊢ e₁ : T₁ !E₁    Γ, x: T₁ ⊢ e₂ : T₂ !E₂
    ----------------------------------------------- (Seq)
    Γ ⊢ let x = e₁; e₂ : T₂ !(E₁ ∪ E₂)

Effects compose by **union** in sequential composition.

**Function abstraction (effect closure):**

    Γ, x: T₁ ⊢ body : T₂ !E
    ----------------------------------- (Abs)
    Γ ⊢ fn(x: T₁) -> T₂ !E : T₁ → T₂ !E

The function's declared effect set must be a superset of the body's inferred effects:

    E_body ⊆ E_declared

### 2.6 Comparison with Other Systems

| System | Effect Mechanism | Tracking | Handling |
|--------|-----------------|----------|----------|
| **Baga** | Type annotations `!E` | Compiler-inferred | `catch !E => h` |
| **Koka** | Effect types in signatures | Row-polymorphic inference | `handle ... with` |
| **Eff** | Algebraic effects | Explicit effect types | `handle` blocks |
| **OCaml 5** | Effect handlers | Untracked (runtime) | `match_with` |
| **Rust** | `Result<T, E>` / `Option<T>` | Type-level (monadic) | `match` / `?` operator |

**Key differences from Rust.** Rust encodes effects as *values* (`Result`, `Option`). Baga encodes effects as *type dimensions*. The distinction:

- Rust: `fn read(path: &str) -> Result<String, io::Error>` — the effect is in the value space.
- Baga: `fn read(path: str) -> str !IO !NotFound` — the effect is in the type space.

In Rust, you can ignore a `Result` (with a warning). In Baga, you cannot ignore an effect — it is a type error.

**Key differences from Koka.** Koka uses full row polymorphism with effect variables in type signatures. Baga simplifies: effects are a finite, named set with union composition. No higher-order effect polymorphism. The trade-off: less expressiveness, more predictability.

### 2.7 Mathematical Properties: Join-Semilattice

**Theorem.** The set of all finite effect sets 𝒫_fin(𝔼) forms a **join-semilattice** under set union:

    (𝒫_fin(𝔼), ∪, ∅)

where:
- The join operation is ∪ (effect composition).
- The bottom element is ∅ (purity).
- The operation is associative: (E₁ ∪ E₂) ∪ E₃ = E₁ ∪ (E₂ ∪ E₃)
- The operation is commutative: E₁ ∪ E₂ = E₂ ∪ E₁
- The operation is idempotent: E ∪ E = E

**Proof sketch.** Finite subsets of any set form a join-semilattice under union. Since 𝔼 is a set and effect sets are finite subsets of 𝔼, the result follows directly. □

**Corollary.** Effect composition is deterministic and order-independent. The order of `catch` clauses does not affect the final type:

    e catch !IO => h₁ catch !NotFound => h₂  :  T !(E \ {!IO, !NotFound})
    e catch !NotFound => h₂ catch !IO => h₁  :  T !(E \ {!IO, !NotFound})

Both yield the same type.

**Definition (Effect Subtyping).** We define a subtyping relation on effect-annotated types:

    T !E₁  ≤  T !E₂   ⟺   E₁ ⊆ E₂

A type with fewer effects is a subtype of a type with more effects. A pure value (`E = ∅`) is a subtype of any effect-annotated value of the same base type:

    T ≤ T !E   for all E

This is **width subtyping** on the effect dimension.

## 3. Specification Theory

### 3.1 Design by Contract

Bertrand Meyer's Design by Contract (1986, Eiffel) established the paradigm:

- **Preconditions** P: what the caller must guarantee before calling f.
- **Postconditions** Q: what f guarantees upon return.
- **Invariants** I: what remains true throughout execution.

The contract is: {P} f {Q} — if P holds before the call, Q holds after.

### 3.2 Baga's Specification System

Baga's specs differ from classical DbC in a fundamental way: **specifications are separate from implementations and are checked by the compiler at compile time**.

```baga
spec сортирай {
    input:
        arr: i64
    output: i64
    guarantees:
        - output is sorted
        - output has same elements as input
}

fn сортирай(arr: i64) -> i64 {
    return arr
}
```

The spec and the function are **separate declarations**. The compiler associates them by name matching and checks:

1. **Signature conformance**: input/output types match.
2. **Contract verification** (`requires` / `ensures`): mechanically discharged by the static verifier for a defined arithmetic fragment (see §8), or checked dynamically at runtime.

Executable fragment used by `--verify`:

```baga
spec abs_val {
    input:  n: i64
    output: i64
    ensures: output >= 0, output >= n, output >= 0 - n
}
fn abs_val(n: i64) -> i64 {
    if n >= 0 { return n } else { return 0 - n }
}
```

### 3.3 Formal Specification Semantics

**Definition (Specification).** A Baga specification is a tuple:

    S = (name, inputs, output, requires, ensures, decreases?)

where:
- name ∈ Identifier
- inputs = [(x₁, T₁), ..., (xₙ, Tₙ)]
- output = T_ret
- requires = [R₁, ..., Rₘ] — precondition predicates over inputs
- ensures = [E₁, ..., Eₖ] — postcondition predicates over inputs and `output`
- decreases? — optional well-founded measure for termination (M6)

**Definition (Spec-Function Association).** A function f is associated with spec S iff `name(f) = name(S)` (at most one spec per name).

**Definition (Signature Conformance).**

    typeof(params(f)) = inputs(S)  ∧  typeof(return(f)) = output(S)

### 3.4 Verification Conditions

**Definition (Verification Condition).** For pure `f` with body paths Π:

    VC(f, S) ≡ ∀ path π ∈ Π.  (requires ∧ path_π ∧ ret_π)  ⇒  ensures[output ↦ ret_π]

Equivalently, the verifier shows that for every path,

    requires ∧ path_π ∧ ¬ensures   is unsatisfiable over ℤ

inside the fragment of §8. Outside the fragment the path is marked UNKNOWN — never falsely PROVEN.

**Implemented.** Signature check; static `--verify` (M0–M13); runtime contracts; property-based `--test-specs`.

### 3.5 Connection to Hoare Logic

Baga contracts are Hoare triples with explicit preconditions:

    { requires }  f  { ensures }

**Consequence:**

    {P'} f {Q'}    P ⇒ P'    Q' ⇒ Q
    -----------------------------------
    {P} f {Q}

**While (invariant I, condition b):**

    {I}  assert I          (init)
    {I ∧ b}  body  {I}     (preservation)
    ─────────────────────────────────
    {I} while b { body } {I ∧ ¬b}

Trusted post-loop use of I only if both init and preservation are PROVEN (soundness gate).

**Recursion (assume–guarantee):** callee `requires` discharged at call site; callee `ensures` assumed for the result iff body is verifiable — partial correctness unless `decreases` proves termination (full correctness).

### 3.6 The Spec as Communication Protocol

Specs are a **protocol between human and AI**:

1. Human writes the contract (intent, bounds, measures).
2. AI writes the implementation.
3. The compiler is the judge (`--verify` / runtime / `--test-specs`).

This inverts the traditional workflow. The spec is not documentation — it is the **primary artifact**. The implementation is secondary, derivable, replaceable.

## 4. Proof Extraction

### 4.1 Proof Extraction in Coq

In Coq, proof extraction is the process of compiling constructive proofs into executable programs:

    Proof → Program

A proof of `∀n: nat. ∃m: nat. m = n + n` extracts into a function `nat → nat` that computes the witness. The direction is: **from proof to code**.

### 4.2 Baga's Reverse Direction

Baga performs the **reverse** extraction:

    Program → Proof Sketch

Given an implementation, the compiler extracts human-readable theorems that describe what the program does and why it terminates. These are not formal proofs — they are **proof sketches** that a human (or AI) can verify.

### 4.3 What Gets Extracted

For a function f, the compiler extracts up to five kinds of theorems:

**1. Signature theorem:**

    theorem f_signature:
        ∀ x₁: T₁, ..., xₙ: Tₙ. f(x₁, ..., xₙ) → T_ret

This states the function's type as a logical proposition.

**2. Termination theorem:**

    theorem f_terminates:
        ∀ x₁: T₁, ..., xₙ: Tₙ. terminates(f(x₁, ..., xₙ))
        evidence: <structural evidence>

Evidence includes:
- Base cases (early returns)
- Decreasing arguments (for recursive calls)
- Bounded loops (for iterative functions)
- Return path count

**Example:**

```
proofs for факториел:
  theorem факториел_terminates:
    ∀ n: i64. terminates(факториел(n))
    evidence: base case with early return, 2 return paths
```

**3. Purity theorem:**

    theorem f_pure:
        pure(f)

Extracted when f declares no effects (E = ∅). This is a theorem because purity is a **property** — the absence of effects is a meaningful guarantee.

**4. Effect theorem:**

    theorem f_effects:
        effects(f) = {E₁, ..., Eₖ}
        callers must handle: E₁, ..., Eₖ

For effectful functions, the compiler documents exactly which effects callers must handle.

**5. Spec contracts (with static status when `--verify` runs):**

    theorem f_ensures:
        - E₁ [PROVEN | REFUTED | UNKNOWN]     // see §7
        - G₂ [UNVERIFIED]

Guarantees from the associated spec are listed with their verification status.

### 4.4 Formal Extraction Rules

We define the extraction function ⟦·⟧ that maps functions to theorem sets:

    ⟦fn f(x₁: T₁, ..., xₙ: Tₙ) -> T_ret !E { body }⟧ = {
        f_signature:    ∀x̄: T̄. f(x̄) → T_ret
        f_terminates:   ∀x̄: T̄. terminates(f(x̄))  [with evidence(body)]
        f_pure:         pure(f)                     [if E = ∅]
        f_effects:      effects(f) = E              [if E ≠ ∅]
        f_guarantees:   [G₁, ..., Gₖ]              [if spec(f) exists]
    }

**Termination evidence extraction:**

    evidence(body) = {
        base_cases:     count of return statements not in recursive position
        return_paths:   total count of return statements
        decreasing:     arguments that decrease in recursive calls
        loop_bounds:    upper bounds on while/for loops
    }

**Example — Fibonacci (iterative):**

```baga
fn фибоначи(n: i64) -> i64 {
    let mut a: i64 = 0
    let mut b: i64 = 1
    let mut i: i64 = 0
    while i < n {
        let temp = b
        b = a + b
        a = temp
        i = i + 1
    }
    return a
}
```

Extracted:

```
theorem фибоначи_signature:
    ∀ n: i64. фибоначи(n) → i64

theorem фибоначи_terminates:
    ∀ n: i64. terminates(фибоначи(n))
    evidence: while loop with bound n, i increases by 1 each iteration

theorem фибоначи_pure:
    pure(фибоначи)
```

### 4.5 Connections to Related Work

**Knuth's Literate Programming (1984).** Knuth proposed that programs should be written as literature — explanations interspersed with code. Baga's proof extraction automates part of this: the compiler generates the "explanation" (theorems) from the code. The human need not write both code and documentation — the compiler extracts the documentation.

**Dafny's Gradual Verification (2010).** Dafny requires annotations (requires, ensures, decreases) and verifies them mechanically. Baga takes a lighter approach: no annotations required, theorems are extracted automatically, verification is gradual (UNVERIFIED → VERIFIED). The programmer can adopt verification incrementally.

**Lean 4's Theorem Extraction.** Lean extracts formal theorems that are machine-checkable. Baga extracts **readable** theorems that are human-checkable. The trade-off:

| | Lean 4 | Baga |
|---|---|---|
| Formality | Fully formal | Informal sketches |
| Audience | Proof assistants | Humans, AI |
| Checking | Mechanical | Visual/AI-assisted |
| Burden | High (write proofs) | Zero (automatic) |
| Trust | Mathematical | Pragmatic |

### 4.6 The AI Verification Workflow

The complete Baga workflow integrates all three pillars:

```
┌─────────────────────────────────────────────────────────┐
│  1. Human writes spec                                    │
│     spec sort { input: arr: [i64], output: [i64],       │
│       guarantees: [sorted, same elements] }              │
├─────────────────────────────────────────────────────────┤
│  2. AI writes implementation                             │
│     fn sort(arr: [i64]) -> [i64] { ... }                │
├─────────────────────────────────────────────────────────┤
│  3. Compiler checks signature conformance                │
│     ✓ input types match                                  │
│     ✓ output type matches                                │
├─────────────────────────────────────────────────────────┤
│  4. Compiler extracts proof sketches                     │
│     theorem sort_signature: ∀ arr. sort(arr) → [i64]    │
│     theorem sort_terminates: ∀ arr. terminates(sort(arr))│
│     theorem sort_pure: pure(sort)                        │
│     theorem sort_guarantees:                             │
│       - output is sorted [UNVERIFIED]                    │
│       - same elements [UNVERIFIED]                       │
├─────────────────────────────────────────────────────────┤
│  5. Human (or AI) reviews proof sketches                 │
│     → Accept, reject, or request revision                │
└─────────────────────────────────────────────────────────┘
```

The key insight: **the compiler does not prove correctness — it makes correctness visible**. The human remains the judge. The AI remains the author. The compiler is the mediator that ensures neither can ignore the other.

## 5. Self-Hosting and Bootstrapping

### 5.1 The Bootstrap Problem

A self-hosting compiler is a compiler written in the language it compiles. This creates a circular dependency:

    To compile baga, you need baga.
    To have baga, you need to compile baga.

The resolution is a **bootstrap chain**: start with a compiler written in a different language (C), use it to compile the self-hosted compiler, and verify the result.

### 5.2 The Bootstrap Ritual

Baga's bootstrap procedure:

```
Stage 1:  baga₁ (C compiler) compiles compiler.baga → C → gcc → baga₂
Stage 2:  baga₂ compiles compiler.baga → C → gcc → baga₃
Stage 3:  verify baga₂ == baga₃ (binary equality)
```

If baga₂ == baga₃, the compiler is a **fixed point** of the compilation process.

### 5.3 Fixed-Point Theorem

**Definition (Compilation Function).** Let C_L be the compilation function for language L:

    C_L : Source(L) → Binary

For a self-hosting compiler, the source is written in L itself:

    C_L : Source(L) → Binary,  where source(C_L) ∈ Source(L)

**Definition (Fixed Point).** A compiler C* is a fixed point of the compilation function if:

    C_L(C*) = C*

That is, compiling the compiler with itself produces an identical binary.

**Theorem (Bootstrap Correctness).** If baga₂ == baga₃, then the self-hosted compiler is a fixed point of the compilation function.

**Proof.** Let S be the source of compiler.baga. Then:
- baga₂ = C₁(S) where C₁ is the C bootstrap compiler
- baga₃ = baga₂(S) = C₁(S)(S)

If baga₂ == baga₃, then C₁(S) = C₁(S)(S), which means the compiled compiler, when applied to its own source, reproduces itself. This is precisely the fixed-point condition. □

**Note.** This does not prove the compiler is *correct* — only that it is *consistent*. A compiler that consistently produces wrong code would also satisfy the fixed-point property. Correctness is established separately by the test suite and spec verification.

### 5.4 Baga's Self-Hosting Implementation

The self-hosted compiler is approximately 960 lines of Baga, organized as:

```
self/
├── lexer.baga      # Tokenizer (UTF-8 aware, Cyrillic identifiers)
├── parser.baga     # Recursive descent parser
└── compiler.baga   # AST builder + C code generator
```

The compiler uses `Vec` (dynamic arrays) as its primary data structure for AST representation:

```baga
fn ast_kind(nk: Vec, nt: Vec, fc: Vec, ns: Vec, kind: i64, text: str) -> i64 {
    let idx = vec_len(nk)
    vec_push(nk, kind)
    vec_push_str(nt, text)
    vec_push(fc, 0 - 1)
    vec_push(ns, 0 - 1)
    idx
}
```

The AST is stored as four parallel arrays:
- `nk` — node kind (integer tag)
- `nt` — node text (string payload)
- `fc` — first child index (linked list)
- `ns` — next sibling index (linked list)

This is a **left-child-right-sibling** tree representation, chosen for its simplicity in a language without algebraic data types.

### 5.5 Notable Bugs in Self-Hosting

The bootstrap process revealed subtle bugs that illustrate the importance of the fixed-point test:

**The Escape Sequence Bug.** The tokenizer must convert the two-character sequence `\n` (backslash, n) into a single newline character (ASCII 10). The initial self-hosted implementation kept the literal backslash-n, producing incorrect string constants. This manifested as:

    Expected: "line1\nline2"  (with actual newline)
    Got:      "line1\\nline2" (with literal backslash-n)

The fix required the tokenizer to recognize escape sequences during lexing:

    if c == 92 {   // backslash
        pos = pos + 1
        let next = char_at(src, pos)
        if next == 110 { emit(10) }       // \n → newline
        if next == 116 { emit(9) }        // \t → tab
        if next == 92  { emit(92) }       // \\ → backslash
        if next == 34  { emit(34) }       // \" → quote
    }

**The Implicit Return Bug.** In Baga, the last expression in a function body is implicitly returned (if no explicit `return` precedes it). The self-hosted compiler initially failed to emit the `return` statement for trailing expressions, causing functions to return garbage. The fix: detect when the last statement in a function body is an expression (not a return/if/while) and wrap it in an implicit return.

### 5.6 The C Transpiler Backend

Baga compiles to C, which is then compiled by gcc:

    Baga source → AST → C source → gcc → binary

The C backend was chosen for its universality: `gcc` has been available on virtually every Unix system since 1987. This aligns with Baga's philosophy of zero dependencies.

The transpilation is compositional:

    ⟦fn f(x: T) -> T' { body }⟧_C = T' f(T x) { ⟦body⟧_C }
    ⟦let x = e⟧_C = auto x = ⟦e⟧_C;  (with appropriate C type)
    ⟦if c { a } else { b }⟧_C = if (⟦c⟧_C) { ⟦a⟧_C } else { ⟦b⟧_C }
    ⟦while c { b }⟧_C = while (⟦c⟧_C) { ⟦b⟧_C }

## 6. Mathematical Foundations Summary

### 6.1 Category Theory: Effects as Monads

In categorical semantics, computational effects are modeled as **monads** (Moggi, 1991). A monad on a category C is a triple (T, η, μ) where:

- T : C → C is an endofunctor
- η : Id → T is the unit (return)
- μ : T² → T is the multiplication (join)

satisfying the monad laws:

    μ ∘ Tη = μ ∘ ηT = id        (unit laws)
    μ ∘ Tμ = μ ∘ μT             (associativity)

In Baga's simplified model, an effect-annotated type T !E can be understood as:

    T !E  ≅  T × E  (simplified product interpretation)

or more precisely, as a monadic type:

    T !E  ≅  M_E(T)

where M_E is the monad associated with effect E. For multiple effects:

    T !E₁ !E₂  ≅  M_{E₁}(M_{E₂}(T))

The order-independence of Baga's effect sets corresponds to the **commutativity** of the monads:

    M_{E₁} ∘ M_{E₂} ≅ M_{E₂} ∘ M_{E₁}

This is a strong property that does not hold for arbitrary monads but is enforced by Baga's design (effects are unordered sets, not sequences).

### 6.2 Lattice Theory: Effect Sets

The effect system's mathematical structure is a **join-semilattice**:

**Definition.** A join-semilattice is an algebraic structure (S, ∨) where ∨ is associative, commutative, and idempotent.

For Baga's effects:

    S = 𝒫_fin(𝔼)     (finite subsets of the effect universe)
    ∨ = ∪              (set union)
    ⊥ = ∅              (purity / no effects)

The partial order is:

    E₁ ≤ E₂  ⟺  E₁ ⊆ E₂

**Properties:**

1. **Monotonicity of composition.** If E₁ ⊆ E₁' and E₂ ⊆ E₂', then E₁ ∪ E₂ ⊆ E₁' ∪ E₂'.
2. **Least upper bound.** For any two effect sets E₁, E₂, their join E₁ ∪ E₂ is the least effect set containing both.
3. **No greatest element** (in general). There is no "maximally effectful" type unless 𝔼 is finite and we take E = 𝔼.

**Theorem (Effect Inference Completeness).** The inferred effect set for any expression is the least upper bound of all effects that may occur during evaluation.

**Proof sketch.** By structural induction on expressions:
- Base case (literal): E = ∅ (the bottom element).
- Function call: E = E_callee (inherited).
- Sequential composition: E = E₁ ∪ E₂ (join).
- Catch: E = E_body \ {E_handled} (removal).
- If/match: E = ∪ᵢ E_armᵢ (join over branches).

Each step computes the lub of constituent effects. □

### 6.3 Logic: The Curry-Howard-Lambek Correspondence

The Curry-Howard correspondence extends to a three-way correspondence (Lambek, 1980):

| Logic | Type Theory | Category Theory | Baga |
|-------|-------------|-----------------|------|
| Proposition | Type | Object | `T` |
| Proof | Program | Morphism | `fn` |
| Implication | Function type | Exponential | `->` |
| Conjunction | Product | Product | `struct` |
| Disjunction | Sum type | Coproduct | `enum` |
| ∀ quantifier | Dependent product | Right adjoint | spec `∀` |
| ∃ quantifier | Dependent sum | Left adjoint | (implicit) |
| Modus ponens | Application | Evaluation | `f(x)` |
| Cut elimination | β-reduction | Composition | inlining |

Under this correspondence, Baga's three pillars map to:

1. **Specs** = logical propositions (what should be true)
2. **Effects** = modal operators (what may happen)
3. **Proofs** = witnesses (evidence of correctness)

The effect modality can be understood in terms of **modal logic**:

    ◇E P  ≡  "P may be achieved with effect E"
    □E P  ≡  "P necessarily requires handling effect E"

Baga's type system enforces □E: if a computation has effect E, the context **must** handle E. This is a necessity modality, not a possibility.

### 6.4 Fixed-Point Theory: Self-Hosting

The self-hosting property connects to **domain theory** and the theory of recursive definitions.

**Definition (Scott Domain).** A Scott domain is a pointed directed-complete partial order (dcpo) with a least element ⊥.

**Theorem (Kleene Fixed-Point Theorem).** Every continuous function f on a Scott domain has a least fixed point:

    lfp(f) = ⨆ₙ fⁿ(⊥)

For self-hosting compilers, the iteration is:

    C₀ = ⊥                    (no compiler)
    C₁ = bootstrap(C₀)        (C compiler, the starting point)
    C₂ = C₁(compiler.baga)    (first self-hosted generation)
    C₃ = C₂(compiler.baga)    (second self-hosted generation)
    ...
    Cₙ₊₁ = Cₙ(compiler.baga)

The fixed-point test checks C₂ == C₃, which is a **sufficient condition** for convergence:

    C₂ == C₃  ⟹  ∀n ≥ 2. Cₙ == C₂

**Proof.** If C₂ == C₃, then C₂(compiler.baga) == C₃(compiler.baga) (since they are the same binary applied to the same source). But C₃(compiler.baga) = C₄, so C₃ == C₄. By induction, Cₙ == C₂ for all n ≥ 2. □

This is why the bootstrap ritual requires only two generations, not an infinite sequence.

| Baga Concept | Mathematical Structure | Key Property |
|---|---|---|
| Types | Simply typed λ-calculus | Strong normalization |
| Effect sets | Join-semilattice (𝒫_fin(𝔼), ∪, ∅) | Commutative, idempotent |
| Effect composition | Monadic composition | Associativity |

## 7. Static Verification Theory  
*(Fourier–Motzkin, Farkas, ℤ-tightening, nonlinear envelopes)*

> This section is the part that does not appear in ordinary software-engineering curricula. It is the mathematical content of `src/verify.c` milestones M0–M13.

### 7.1 The decision problem and trichotomy

Fix a pure function `f` with contract `{R} f {E}` over `i64`. After symbolic execution we obtain a finite set of *path obligations*. For each path π with path condition Γ_π and return expression r_π, the verifier must classify:

    VC_π  ≡   R ∧ Γ_π  ⇒  E[output ↦ r_π]

equivalently, decide satisfiability of

    Σ_π  ≡   R ∧ Γ_π ∧ ¬E[output ↦ r_π]

**Definition (Verdict trichotomy).**

| Verdict | Meaning | Obligation on the engine |
|---------|---------|---------------------------|
| **PROVEN** (ДОКАЗАНО) | Σ_π is unsatisfiable over ℤ | Must be correct: never a false proof |
| **REFUTED** (ОБРОЧЕНО) | ∃ concrete ℤ-witness violating E | Witness must be realizable (no free abstracts) |
| **UNKNOWN** (НЕ МОГА ДА РЕША) | Outside fragment / incomplete | Always safe; never asserts |

Rice's theorem: *arbitrary* semantic properties of programs are undecidable. Baga therefore works in a **syntactically restricted fragment** ℱ (defined below) where PROVEN is backed by linear arithmetic unsatisfiability, not by hope.

### 7.2 Linear forms and polyhedral path conditions

**Definition (Linear form over ℚ).** A linear form is

    ℓ = c₀ + Σᵢ cᵢ · xᵢ    with   cᵢ ∈ ℚ, xᵢ free symbols.

The symbolic state maps program variables to linear forms (or marks them nonlinear). Vector lengths are tracked as linear forms in a separate map; element axioms `v[*] ≥ c` are quantified templates instantiated at each `vec_get`.

**Definition (Atomic constraint).**

    ℓ  ⋖  0     where ⋖ ∈ { < , ≤ }

**Definition (Path formula).** A path condition is a DNF of conjunctions of atomic constraints — a finite union of convex polyhedra in ℚⁿ. Boolean structure of `if` conditions is converted by De Morgan into this DNF (`bool_to_dnf`).

### 7.3 Fourier–Motzkin elimination

**Theorem (Fourier–Motzkin, classical).** Satisfiability of a finite system of linear inequalities over ℚ is decidable by successive variable elimination: to eliminate x, partition constraints into those with positive / negative / zero coefficient of x and form all cross-bounds. The system is sat iff the residual system after eliminating all variables is sat.

Baga implements FM as the core engine for path obligations. Complexity is doubly exponential in the worst case in the number of variables — acceptable because path systems are small and the alternative (external SMT) violates the zero-dependency invariant.

**Corollary (Rational completeness for LRA).** Inside pure linear real arithmetic, FM is a complete decision procedure. Combined with the trichotomy, every linear obligation is PROVEN or REFUTED (or UNKNOWN only if conversion to DNF fails for other reasons).

### 7.4 Farkas certificates and the meaning of PROVEN

**Theorem (Farkas' lemma, geometric form).** A system A x ≤ b over ℚ is unsatisfiable iff there exists λ ≥ 0 such that λᵀ A = 0 and λᵀ b < 0 (a nonnegative linear combination of inequalities yielding a contradiction 0 ≤ −ε).

Operationally, when FM reports unsat, the combination that produced the empty face is a **Farkas certificate**: a checkable proof object that Σ_π has no rational solution. Baga's PROVEN path is exactly "¬E is unsat under R ∧ Γ", i.e. R ∧ Γ ⊨ E over ℚ, hence over ℤ after the tightening of §7.5.

### 7.5 Integer tightening (M7) — closing the ℤ/ℚ gap

Over ℤ, for integer-valued linear forms with integer coefficients:

    ℓ < 0    ⟺    ℓ ≤ −1

**Definition (Integer tightening).** Before FM, every strict inequality on integer forms is rewritten to a non-strict one shifted by one.

**Proposition (Exactness on ℤ).** Tightening preserves the set of integer solutions and does not invent rational-only solutions that would create false PROVEN. The classic trap

    n > 0  ⊬_ℚ  n ≥ 1     but    n > 0 ⊢_ℤ n ≥ 1

is closed: after tightening, `n ≥ 1` is PROVEN from `n > 0`.

This is standard in integer linear programming and almost never taught in software courses; without it, verifiers either lie or stay forever weak on the most basic integer facts.

### 7.6 Symbolic execution rules (core fragment ℱ₀)

States σ = (env, path, lengths, axioms, derived-symbols).

| Construct | Rule |
|-----------|------|
| `let x = e` | bind x ↦ ⟦e⟧_σ if linear; else mark nonlinear / allocate product symbol |
| `if b then t else e` | DNF-split on b and ¬b; fork path; inject product axioms (M13) |
| `while b invariant I` | prove I at entry; prove I preserved under b; exit with I ∧ ¬b only if trusted |
| `return e` | snapshot (path, ⟦e⟧) as obligation |
| `vec_get(v,i)` | bound obligations 0 ≤ i < len(v); instantiate element axioms |
| call `g(args)` with spec | discharge g.requires; assume g.ensures on fresh result (M5) |

**Unsupported** constructs mark the function SKIPPED/UNKNOWN — honest incompleteness, never silent accept.

### 7.7 Recursion and termination

**Partial correctness (M5).** Recursive calls use the callee contract as induction hypothesis. Verdicts are labelled partial: they do not claim termination.

**Full correctness (M6).** A `decreases: D` measure requires:

    R ⇒ D ≥ 0
    at each self-call: D' ≥ 0 ∧ D' < D

under the path condition. This is well-founded induction on (ℕ, <) (or a lexicographic extension). A non-decreasing measure is REFUTED with a witness; the function falls back to partial correctness.

### 7.8 Nonlinear envelope: product symbols (M8–M12)

Nonlinear integer arithmetic (NIA) is undecidable. Baga does **not** decide NIA. It uses a **factor-aware envelope**:

**Definition (Derived product symbol).** For non-constant product of linear forms f · g, allocate fresh p with record (f, g) ∈ Π. Similarly q for f/g, r for f%g.

**Axiom injection.** Only universally valid schemas, often conditioned on path facts about f, g:

| Schema | Hypothesis | Conclusion |
|--------|------------|------------|
| Square | — | v·v ≥ 0, v·v ≥ v, v·v ≥ −v, (v±1)² ≥ 0 |
| Sign table | sign bounds on f,g | matching sign of fg |
| Mono | f≥0, g≥1 | fg ≥ f (sym.) |
| Const div/mod | d≠0, sign(n) | C trunc laws; 0 ≤ n%d < \|d\| if n≥0 |
| Floor | n≥0, d>0 | d·(n/d) ≤ n |
| Rebuild | both n/d and n%d | n = d·q + r |
| Var div | m≥1, n≥0 | 0 ≤ n/m ≤ n, 0 ≤ n%m < m |
| AM-GM form | f², g², fg present | f² + g² − 2fg ≥ 0 |

**Witness soundness.** Free inputs are searched; product/div/mod values are *derived* from factors, never free. A **conclusiveness gate** rejects refutations that only work for unrealizable abstract symbols (the M8 false-alarm class).

### 7.9 Nonlinear guards and bitwise envelope (M13)

**Products in conditions.** `bool_to_dnf` threads the derived-symbol list, so a guard `n*n ≥ 1` becomes a linear constraint on a product symbol, not an automatic UNKNOWN. After each `if`/`while` decode, axiom injection runs so both forks inherit e.g. n·n ≥ 0.

**Bitwise without bitvectors.** Full BV is decidable but exponential and alien to the polyhedral core. M13 admits only **linear rewrites / residue axioms**:

- n \| 0 = n, n & 0 = 0, n ⊕ 0 = n, n ⊕ n = 0, n & (−1) = n  
- n & 1 ∈ {0,1} over two's complement (explicitly **not** C `n % 2` on negatives)  
- n ≪ k = n · 2ᵏ for constant k ∈ [0,62] (unbounded-ℤ model)  
- n ≫ k as trunc n/2ᵏ with axioms under n ≥ 0  

Anything else bitwise remains nonlinear → UNKNOWN.

### 7.10 Soundness theorems (sketch)

**Theorem (PROVEN is sound).**  
If `--verify` reports PROVEN for ensures E, then every terminating execution of the body on inputs satisfying requires yields a return value satisfying E (under the idealized semantics of div/mod/shift used by the injector).

*Proof idea.* Every PROVEN path has R ∧ Γ ∧ ¬E ℚ-unsat after sound axiom injection and integer tightening; axioms are valid on ℤ; unsupported features never produce PROVEN.

**Theorem (REFUTED is sound).**  
A reported counterexample evaluates to a true violation after deriving all product/div/mod/bit symbols from free inputs; conclusiveness re-checks independence from remaining abstracts.

**Corollary (UNKNOWN is safe).** UNKNOWN never claims a false contract.

### 7.11 Complexity and incompleteness map

| Theory | Status | Baga stance |
|--------|--------|-------------|
| LRA (linear real arithmetic) | PSPACE-complete / FM exp | Core decision procedure |
| LIA / Presburger | Decidable, expensive | Approximated via FM + tightening |
| NIA (nonlinear integers) | Undecidable | Envelope schemas only |
| Quantifier-free BV | Decidable, exp | Identity envelope only |
| Arbitrary semantic properties | Undecidable (Rice) | Fragment gate → UNKNOWN |

### 7.12 What this is *not* taught as in software universities

A typical SE bachelor's degree covers none of: polyhedral path conditions, Farkas lemmas, the ℤ/ℚ gap, well-founded decreases measures, assume–guarantee recursion, or sound incompleteness as a first-class design choice. Those topics live in formal methods / PL theory tracks — if at all. Baga embeds them in a zero-dependency C compiler so that AI-written code faces a judge that knows more mathematics than the average bot prompt.

## 8. Open Problems and Future Directions

### 8.1 Extending the decidable envelope

M0–M13 answer a restricted form of:

    What is the largest *practically useful* fragment ℱ ⊇ LRA
    for which a zero-dep verifier can issue sound PROVEN/REFUTED?

Open: cubes and general polynomials; full BV; quantifiers beyond `v[*]` / `sorted`; overflow-aware shifts; feeding verified invariants into `--proofs` export.

### 8.2 Effect Polymorphism and Higher-Order Functions

    map : ∀E. (T → U !E) → [T] → [U] !E

requires effect variables / row polymorphism and richer inference.

### 8.3 Proof Refinement

    UNKNOWN sketch → AI_VERIFIED → HUMAN_VERIFIED → FORMAL (Lean/Coq)

each step increases confidence without full formalization at the base.

### 8.4 Categorical Semantics of Specs

    Spec : C^op → Set

as a fibration: objects map to predicates; morphisms to predicate transformers. Compositional semantics for contract composition.

### 8.5 Concurrency in the verifier

**M14 lands the first `!Par` fragment.** The language has no shared mutable
state (no globals, no closures — `go(f, x)` takes a named function and an `i64`
by value), so data races are impossible by construction and the existing linear
core suffices. Two sound mechanisms:

- **Fork–join determinism.** For a pure, verifiable worker `f`,
  `join(go(f, x)) ≡ f(x)`: the worker's contract is applied via the M5
  assume–guarantee machinery (requires discharged at spawn, ensures assumed
  for the join result). `ensures` of a parallel function is thus proven with
  exactly the sequential machinery (`examples/verify/par_join.baga`).
- **Handle protocols.** Join handles and channels carry a ghost protocol
  state per symbolic variable: `spawn → join | detach`. A second consume
  (join-after-detach is *fatal* at runtime) is REFUTED statically with a
  counterexample — on any input when the path is unconditional
  (`par_detach_bad.baga`). Channels track open/closed: `send` on a
  known-closed channel is provably `-1` (`par_chan.baga`).

Honest frontier (M15+): pair-returning builtins (`chan_recv2`/`try_recv`/
`select2*`), cross-thread channel *content* invariants (rely–guarantee),
mutexes (liveness), `pool_map`, effectful workers.

### 8.6 Arithmetic safety — the ℤ-vs-i64 bridge (M15)

The verifier reasons in idealized ℤ; the runtime is i64. M15 emits one
obligation per arithmetic operation and proves it cannot overflow on its
path (exact bound search over FM — binary search on feasibility, no new
theory), or refutes it with a concrete large-magnitude witness
(`abs(INT64_MIN)`, `n + 1` at `n = INT64_MAX`, `n / m` at `m = 0`). When all
obligations of a function are PROVEN, the idealized model and the runtime
coincide and ensures verdicts become unconditional; otherwise the output
says so. Two soundness fixes shipped with it: **loop havoc** (variables
assigned in a `while` body are havoced before the invariant is assumed —
stale pre-loop values previously made invariants vacuous, a false-PROVEN
hole, `loop_havoc.baga`) and an INT64_MIN-safe rational core (`__int128`
intermediates + conservative bail-out in `fm_sat`). Note:
`docs/thesis-m15-arith-safety.md`.

### 8.7 Channel content invariants (M16)

M16 closes the concurrency chapter: `invariant c[*] >= 1` states "every
payload sent on `c` satisfies the predicate", anchored on the resolved
symbolic channel var (aliases share one invariant). `chan_send` discharges
the predicate or the axiom drops (M3 rule); `chan_recv` instantiates it.
At `go` spawn the caller must prove its invariant covers the worker's
`requires c[*] ...` (a checked obligation); a worker without matching
requires drops the axiom at spawn — rely–guarantee in the small, composing
with M14's fork–join determinism (`chan_inv_par.baga`). The scalar form
`invariant e` doubles as `assume`. Note:
`docs/thesis-m16-channel-invariants.md`.
