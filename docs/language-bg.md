# Езикова Справка на Бага

> Пълна справка за езика Бага: синтаксис, типове, семантика, ефектова система,
> система за спецификации, вградени функции и примери.

Бага (Baga) е компилиран, статично типизиран език, стъпил върху три идеи:

1. **Spec-first верификация** — `spec` е ключова дума; компилаторът проверява
   имплементациите срещу техните спецификации.
2. **Ефекти като измерения на типа** — `str !IO !NotFound` е *различен тип* от
   `str`. Грешките живеят в типовата система, а не като изненади по време на
   изпълнение.
3. **Четими proof sketches** — компилаторът издава четими скици от кода и
   spec-ите; `--verify` добавя сертификати (или честно UNKNOWN) във фрагмента.

Бага се транслира до C и се компилира с `gcc`. Няма зависимости по време на
изпълнение. Идентификаторите могат да се пишат на латиница или кирилица — езикът
е идентичност.

## 1. Първи стъпки

```baga
fn main() {
    print("Здравей, багатуре. Боят започва.")
}
```

```bash
$ baga examples/zdravei.baga
Здравей, багатуре. Боят започва.
```

Всяка програма трябва да дефинира функция `main` без параметри. Изпълнението
започва оттам. Липсата на `main` е грешка при компилация.

## 2. Лексикална структура

### 2.1 Коментари

```baga
// Едноредов коментар — до края на реда.

/* Блоков коментар.
   Блоковите коментари се ВЛАГАТ, така че можете да коментирате код,
   /* който сам съдържа коментари */, безопасно. */
```

### 2.2 Идентификатори

Идентификаторът започва с буква (`a`–`z`, `A`–`Z`), долна черта `_` или който и
да е многобайтов UTF-8 символ (това позволява кирилицата). Следващите символи
могат да бъдат и цифри `0`–`9`.

Всички тези са валидни идентификатори:

```baga
let x = 1
let резултат = 2
let _private = 3
let име_на_потребител = "бага"
```

Ключовите думи са запазени и не могат да се ползват като идентификатори
(виж §2.4).

### 2.3 Литерали

**Цели числа.** По подразбиране са десетични. Поддържат се шестнадесетичен
(`0x`), двоичен (`0b`) и осмичен (`0o`) префикс. Долни черти могат да разделят
цифрите за четимост. Целочислените литерали имат тип `i64`.

```baga
let a = 42          // десетично
let b = 0xFF        // шестнадесетично = 255
let c = 0b1010      // двоично = 10
let d = 0o17        // осмично = 15
let e = 1_000_000   // долните черти се пренебрегват
```

**Дробни числа.** Десетична точка и/или експонента правят литерала дробен, от
тип `f64`.

```baga
let pi = 3.14159
let avogadro = 6.022e23
let tiny = 1.0e-9
```

**Низове.** В двойни кавички, тип `str`. Escape последователности:

| Escape | Значение              |
|--------|-----------------------|
| `\n`   | нов ред               |
| `\t`   | табулация             |
| `\r`   | връщане на каретката  |
| `\\`   | обратна черта         |
| `\"`   | двойна кавичка        |

`str` е C низ и не понася NUL байтове — `\0` в низов литерал е compile
грешка. За сурови байтове ползвайте `bytes` (`x"..."` литерали).

```baga
let поздрав = "Здравей, \"свят\"!\n"
```

**Символи.** В единични кавички, например `'A'`. Символният литерал е цяло
число (байтовата стойност на символа), затова има тип `i64`. Поддържат се
escape-ите: `\n \t \r \\ \' \0`.

```baga
let код = 'A'   // 65
```

**Булеви.** `true` и `false`, тип `bool`.

### 2.4 Ключови думи

```
fn  let  mut  if  else  while  for  in  return  match
struct  impl  spec  enum  true  false  catch  break  continue
```

## 3. Граматика (EBNF)

Граматиката по-долу е описателна; Бага се разбира от рекурсивно-спускащ се
парсер с изкачване по приоритет за бинарните оператори. Точка-запетайките са
незадължителни терминатори на оператори.

```ebnf
program        = { top_level } ;
top_level      = fn_decl | struct_decl | enum_decl | spec_decl ;

(* Декларации *)
fn_decl        = "fn", ident, "(", [ param, { ",", param } ], ")",
                 [ "->", type, { "!", ident } ], ( block | /* празно: forward decl */ ) ;
param          = ident, ":", type ;
struct_decl    = "struct", ident, "{", [ field_decl, { ",", field_decl } ], "}" ;
field_decl     = ident, ":", type ;
enum_decl      = "enum", ident, "{", [ ident, { ",", ident } ], "}" ;
spec_decl      = "spec", ident, "{",
                   "input:", [ param, { param } ],
                   "output:", type,
                   "guarantees:", { "-", free_text },
                 "}" ;

(* Типове *)
type           = "&", type                       (* референция *)
               | "[", type, "]"                  (* масив *)
               | "Vec", [ "<", type, ">" ]       (* вектор; елемент само i64/str *)
               | ident ;                         (* именуван: i32 i64 f64 bool str ... *)

(* Оператори (statements) *)
block          = "{", { statement }, "}" ;
statement      = let_stmt | return_stmt | break_stmt | continue_stmt
               | while_stmt | for_stmt | if_expr | expr_stmt ;
let_stmt       = "let", [ "mut" ], ident, [ ":", type ], "=", expression, [ ";" ] ;
return_stmt    = "return", [ expression ], [ ";" ] ;
break_stmt     = "break", [ ";" ] ;
continue_stmt  = "continue", [ ";" ] ;
while_stmt     = "while", expression, block ;
for_stmt       = "for", ident, "in", expression, block ;
expr_stmt      = expression, [ ";" ] ;

(* Изрази, от най-слаб към най-силен приоритет *)
expression     = assignment ;
assignment     = logical_or, [ assign_op, expression ] ;   (* дясно-асоциативен *)
assign_op      = "=" | "+=" | "-=" | "*=" | "/=" ;
logical_or     = logical_and, { "||", logical_and } ;
logical_and    = equality, { "&&", equality } ;
equality       = comparison, { ( "==" | "!=" ), comparison } ;
comparison     = additive, { ( "<" | ">" | "<=" | ">=" ), additive } ;
additive       = multiplicative, { ( "+" | "-" ), multiplicative } ;
multiplicative = unary, { ( "*" | "/" | "%" ), unary } ;
unary          = ( "-" | "!" | "&" | "*" ), unary | postfix ;
postfix        = primary, { call | index | range | field | try | catch } ;
call           = "(", [ expression, { ",", expression } ], ")" ;
index          = "[", expression, "]" ;
range          = "..", unary ;
field          = ".", ident ;
try            = "?" ;
catch          = "catch", "!", ident, "=>", unary ;

primary        = int_lit | float_lit | str_lit | char_lit
               | "true" | "false"
               | ident                           (* променлива *)
               | struct_lit                      (* Име { поле: израз, ... } *)
               | "(", expression, ")"
               | if_expr | match_expr | block ;

if_expr        = "if", expression, block, [ "else", ( block | if_expr ) ] ;
match_expr     = "match", expression, "{", { match_arm }, "}" ;
match_arm      = ( "_" | unary ), "=>", ( block | expression ), [ "," ] ;
struct_lit     = ident, "{", field_init, { ",", field_init }, "}" ;
field_init     = ident, ":", expression ;
```

## 4. Типове

Бага е статично типизиран с локално извеждане на типовете. Можете да указвате
типовете изрично или да оставите компилаторът да ги изведе от инициализатора.

| Тип     | Значение                                   | Представяне в C  |
|---------|--------------------------------------------|------------------|
| `i32`   | 32-битово цяло число със знак              | `int32_t`        |
| `i64`   | 64-битово цяло число (по подразбиране)     | `int64_t`        |
| `f64`   | 64-битово число с плаваща запетая          | `double`         |
| `bool`  | булев (`true` / `false`)                   | `int`            |
| `str`   | низ (нулево-терминиран, непроменим)        | `const char *`   |
| `Vec`   | динамичен масив (в heap-а)                 | `baga_Vec *`     |
| `Vec<T>` | вектор с анотиран елемент (`i64`, `str`, `f64`, `bytes` или struct тип) | `baga_Vec *`     |
| `Map<K,V>` | хеш-таблица; ключ `i64`/`str`, стойност `i64`/`str`/`f64`/`bytes` | `baga_Map *` |
| `[T]`   | масив от `T`                               | указател         |
| `&T`    | референция към `T`                         | `T *`            |
| `void`  | без стойност (процедури)                   | `void`           |
| struct  | потребителски дефиниран запис              | `struct`         |

### 4.1 Извеждане и числово разширяване

- Целочислен литерал се извежда до `i64`.
- Дробен литерал се извежда до `f64`. Литералите се emit-ват с пълна точност
  (`%.17g`, round-trip на IEEE 754 double) — без загуба на цифри.
- Низов литерал се извежда до `str`.
- `true` / `false` се извеждат до `bool`.

Когато два числови типа се срещнат в бинарна операция, резултатът се разширява:

```
f64  ако който и да е операнд е f64
i64  иначе, ако който и да е операнд е i64
i32  иначе
```

```baga
let x = 10        // i64
let y = 3.5       // f64
let z = x + y     // f64 (i64 се разширява до f64)
```

### 4.2 Типове с ефекти

Всеки тип може да носи маркери за ефекти. `str !IO` означава „низ, но получаването
му извършва IO". Виж §13.

## 5. Променливи и `let` свързвания

```baga
let x = 5                 // непроменим, типът е изведен (i64)
let mut y: i64 = 10       // променим, изричен тип
let име: str = "бага"     // непроменим с анотация

y = y + 1                 // ОК: y е mut
// x = 6                  // (присвояване на непроменим — избягвайте)
```

- `let` въвежда непроменимо свързване.
- `let mut` въвежда променимо свързване, което може да се пренасочва.
- Типовата анотация `: тип` е незадължителна; когато липсва, типът се извежда от
  инициализатора.
- Едно `let` свързване е в областта на видимост на обграждащия блок. Повторното
  дефиниране на име в същата област е грешка (`повторно дефиниране`).

### 5.1 Оператори за присвояване

```baga
x = expr      // обикновено присвояване
x += expr     // x = x + expr
x -= expr     // x = x - expr
x *= expr     // x = x * expr
x /= expr     // x = x / expr
```

Съкратените форми се свеждат до бинарна операция върху целта и стойността.

## 6. Функции

```baga
fn събери(a: i64, b: i64) -> i64 {
    return a + b
}
```

- Параметрите винаги носят изричен тип: `име: тип`.
- При извикване checker-ът сверява бройката **и типовете** на аргументите с
  параметрите; несъответствие е compile-time грешка (`i32`/`i64` са съвместими).
- Връщаният тип следва `->`. Пропуснете го за процедури, които не връщат нищо
  (`void`).
- Ефектите, ако има такива, следват връщания тип: `-> str !IO !NotFound`.
- Функция без тяло (`fn f(x: i64) -> i64`) е предварителна декларация
  (forward declaration).

### 6.1 Връщане на стойности

Използвайте `return expr` за ранно връщане. Стойността на последния израз в блок
също се ползва като имплицитно връщане в позициите на израз (например в клоновете
на `match` и `if`).

```baga
fn макс(a: i64, b: i64) -> i64 {
    if a > b {
        return a
    }
    return b
}
```

### 6.2 Рекурсия

Функциите могат да викат сами себе си. Предварителните декларации позволяват на
взаимно рекурсивни функции да се сочат една друга независимо от реда им.

```baga
fn факториел(n: i64) -> i64 {
    if n <= 1 {
        return 1
    }
    return n * факториел(n - 1)
}
```

## 7. Управление на потока

### 7.1 `if` / `else`

Условието трябва да е `bool`. Поддържат се вериги от `else if`.

```baga
fn знак(n: i64) -> str {
    if n > 0 {
        return "положително"
    } else if n < 0 {
        return "отрицателно"
    } else {
        return "нула"
    }
}
```

`if` е и израз и може да стои от дясната страна на `let` или `return`.

### 7.2 `while`

```baga
let mut i: i64 = 0
while i < 10 {
    print(i)
    i = i + 1
}
```

### 7.3 `for`

`for` обхожда диапазон `lo..hi`. Диапазонът е полуотворен: включва `lo` и
изключва `hi`. Променливата на цикъла е ново свързване от тип `i64`, валидно в
тялото.

```baga
for i in 0..15 {
    print(i)        // 0, 1, 2, ... 14
}
```

### 7.4 `break` и `continue`

```baga
let mut i: i64 = 0
while true {
    i = i + 1
    if i == 3 { continue }   // прескочи към следващата итерация
    if i > 5 { break }       // излез от цикъла
    print(i)
}
```

## 8. `match`

`match` сравнява стойност срещу шаблони и оценява първия съвпадащ клон.
Шаблоните могат да бъдат литерали, идентификатори или заместващият символ `_`.
Тялото на всеки клон е израз или блок.

```baga
fn описание(n: i64) -> i64 {
    let резултат = match n {
        0 => 100,
        1 => 200,
        2 => 300,
        _ => 999,
    }
    return резултат
}
```

Заместващият символ `_` съвпада с всичко и по конвенция се поставя последен.
Клон, чието тяло е гол израз, връща тази стойност от обграждащата функция.

Когато сравняваната стойност е **сборен enum** (§11.1), шаблоните са
`Variant(свързване)`, голо `Variant` за варианти без payload, или `_`:

```baga
enum Res { Ok(i64), Err(str) }

fn describe(r: Res) -> str {
    return match r {
        Ok(v) => "успех",
        Err(e) => e,
    }
}
```

`match`-ът трябва да е **изчерпателен** — проверителят дава грешка с името
на липсващия вариант (`не е пълен — липсва вариант 'Err' (или добави '_')`),
а всички клони трябва да са от един и същ тип. Шаблон, който не е вариант на
enum-а на стойността, се отхвърля. `match` върху стойности, които не са
enum, пази правилото „първият съвпадащ клон печели" отгоре, без проверка за
пълнота. Клон с гол израз за тяло работи и във функции `-> void`, където
стойността се отхвърля.

## 9. Оператори и приоритет

От най-слаб към най-силен:

| Приоритет | Оператори                         | Асоциативност |
|-----------|-----------------------------------|---------------|
| 0 (най-слаб)| `=` `+=` `-=` `*=` `/=`         | дясна         |
| 1         | `\|\|`                            | лява          |
| 2         | `&&`                              | лява          |
| 3         | `==` `!=`                         | лява          |
| 4         | `<` `>` `<=` `>=`                 | лява          |
| 5         | `+` `-`                           | лява          |
| 6         | `*` `/` `%`                       | лява          |
| 7         | унарни `-` `!` `&` `*`            | дясна         |
| 8 (най-силен)| постфиксни `()` `[]` `..` `.` `?` `catch` | лява |

### 9.1 Обобщение на операторите

| Категория   | Оператори                                  |
|-------------|--------------------------------------------|
| Аритметични | `+` `-` `*` `/` `%`                        |
| Сравнение   | `==` `!=` `<` `>` `<=` `>=`                |
| Логически   | `&&` `\|\|` `!`                            |
| Присвояване | `=` `+=` `-=` `*=` `/=`                    |
| Референция  | `&` (вземане на адрес) `*` (дерeфериране)  |
| Диапазон    | `..`                                       |
| Ефектови    | `?` (разпространяване) `catch !E => handler` |

Двусимволните оператори, разпознавани от лексера:

```
->  =>  ..  ==  !=  <=  >=  &&  ||  <<  >>  +=  -=  *=  /=
```

Аритметиката изисква числови операнди; прилагането на `+` върху низ и цяло число
например е грешка при компилация.

## 10. Структури (struct)

`struct` е именуван запис от типизирани полета.

```baga
struct Точка {
    x: f64,
    y: f64,
}
```

Създавайте стойности със структурен литерал и достъпвайте полета с `.`:

```baga
fn разстояние(a: Точка, b: Точка) -> f64 {
    let dx = a.x - b.x
    let dy = a.y - b.y
    return dx * dx + dy * dy
}

fn main() {
    let a = Точка { x: 0.0, y: 0.0 }
    let b = Точка { x: 3.0, y: 4.0 }
    print(разстояние(a, b))   // 25
}
```

Достъпът до поле, което не съществува в структурата, е грешка
(`непознато поле`). Конструирането на недекларирана структура е грешка
(`непознат struct`).

## 11. Изброими типове (enum)

`enum` декларира набор от именувани варианти. Вариантите са целочислени,
номерирани от `0` по ред на декларация, и могат да се ползват навсякъде, където
се очаква `i64`.

```baga
enum Цвят {
    Червено,   // 0
    Зелено,    // 1
    Синьо,     // 2
}

fn име(ц: i64) -> str {
    match ц {
        0 => "червено",
        1 => "зелено",
        2 => "синьо",
        _ => "непознато",
    }
}

fn main() {
    let c = Зелено       // 1
    print(име(c))        // зелено
}
```

### 11.1 Сборни типове (sum types, L3)

Един `enum` може да даде на вариант **payload** тип — така става сборен тип
(tagged union):

```baga
enum Res { Ok(i64), Err(str) }
enum Opt { Some(str), None }

fn unwrap_or(r: Res, dflt: i64) -> i64 {
    return match r { Ok(v) => v, _ => dflt }
}

fn main() {
    let r = Ok(42)              // конструкция: Variant(payload)
    let n: Opt = None           // вариантите без payload остават голи
    print(unwrap_or(r, -1))     // 42
}
```

Конструкцията е `Variant(payload)` за вариантите с payload и голото име
`Variant` за останалите; голяма референция към вариант с payload е грешка
при компилация. Payload-ът може да е всеки деклариран тип, включително
struct (`enum Shape { Dot, Circle(Point) }`).

Правила на проверителя:

- Типът е номинален — `enum Res` е собствен тип, **не** `i64`; не може да
  подадете `Res` там, където се очаква `i64`, нито обратното.
- Вариантите могат да се **повтарят между enum-и** — ползвайте `Enum::Variant`
  (A1). Голият `Ok(x)` гърми, когато е нееднозначен. Два пъти същото име
  **в един enum** остава грешка.
- Броят аргументи и типът на payload-а се проверяват (`конструкторът 'Ok'
  очаква 1 аргумент`).
- `match` върху сборен enum ползва вариантни шаблони със свързвания и трябва
  да е изчерпателен — вж. §8.

C бекендът свежда сборния enum до тагната структура с `union` на payload-ите
и по един `static inline` конструктор на вариант. LLVM бекендът ползва
еквивалентното `{ i64 tag, [N x i64] }` разположение (LLVM няма union-и —
областта е i64 масив по най-тежкия payload) с лениви IR конструктори;
двата бекенда съвпадат байт по байт (оракъл: `examples/sum_enum.baga`).

Честни ограничения на v1:

- Няма дженерици — конкретен enum на място; при няколко Result — `Enum::Ok`.
- Точно един payload тип на вариант; за няколко полета ползвайте struct.
- **A2:** `Vec<Res>` и `Map<K, Res>` работят (box path като при struct).
- Ациклични графове struct↔sum enum се емитират в топологичен ред, така че
  **сборният enum може да е поле на struct** (`struct Hold { r: Res }`).

## 12. Низове и вектори (вградени функции)

видими; не е нужен import.

### 12.1 Изход

| Сигнатура | Описание |

### 12.2 Низови операции

| `char_at(s: str, i: i64) -> i64` | Байтовата стойност на символа на индекс `i`. |
| `substr(s: str, a: i64, b: i64) -> str` | Подниз от индекс `a` (включително) до `b` (изключително). |
| `concat(a: str, b: str) -> str` | Слепва два низа в нов низ. |
| `str_eq(a: str, b: str) -> bool` | Истина, ако низовете са байтово равни. |
| `chr(c: i64) -> str` | Едносимволен низ от байтова стойност. |
| `ord(s: str) -> i64` | Байтовата стойност на първия символ на `s` (0 ако е празен). |
| `i64_to_str(x: i64) -> str` | Десетичен запис на `x`. |
| `f64_to_str(x: f64) -> str` | `%g` запис на `x` (целите стойности се печатат без десетична точка). |

### 12.3 Файлов вход/изход

| Сигнатура | Описание |
|-----------|----------|
| `read_file(path: str) -> str !IO` | Чете цял файл. Носи ефекта `!IO`. Връща `""`, ако файлът не може да се отвори. |

Понеже `read_file` има ефекта `!IO`, извикването му задължава викащия или да
декларира `!IO` в собствения си връщан тип, или да го обработи с `catch`
(виж §13).

### 12.4 Вектори (динамични масиви)

`Vec` е динамичен масив в heap-а, който расте. Всеки вектор носи тип на
елементите си — `Vec<i64>`, `Vec<str>`, `Vec<f64>`, `Vec<bytes>` или
`Vec<НякойStruct>` — който се фиксира при първия `vec_push`/`vec_set`.
Смесването на типове в един вектор е грешка при компилация.

| Сигнатура | Описание |
|-----------|----------|
| `vec_new() -> Vec` | Създава празен вектор с неизвестен елементен тип. |
| `vec_len(v: Vec) -> i64` | Брой елементи. |
| `vec_push(v: Vec, x: i64 \| str \| f64 \| bytes \| struct)` | Добавя елемент в края; първият push фиксира елементния тип. |
| `vec_get(v: Vec, i: i64) -> i64 \| str \| f64 \| bytes \| struct` | Чете елемента на индекс `i` (елементния тип на вектора). |
| `vec_set(v: Vec, i: i64, x: i64 \| str \| f64 \| bytes \| struct)` | Презаписва елемента на индекс `i`. |
| `vec_slice(v: Vec, a: i64, b: i64) -> Vec` | Нов вектор с елементите `[a, b)`. Извън-обхватни граници се **отрязват** (clamp), не са грешка (за разлика от `vec_get`/`vec_set`, които прекратяват с bounds съобщение). |
| `vec_concat(v: Vec, w: Vec) -> Vec` | Нов вектор: `v`, последван от `w` (същия елементен тип). |
| `vec_push_str(v: Vec, s: str)` | Псевдоним на `vec_push` за низове (стар код). |
| `vec_get_str(v: Vec, i: i64) -> str` | Псевдоним на `vec_get` за низове (стар код). |
| `vec_set_str(v: Vec, i: i64, s: str)` | Псевдоним на `vec_set` за низове (стар код). |

Векторите са референтни стойности: `let b = a` сочи към същото хранилище —
push през `b` се вижда през `a` (LP5 сонда).

```baga
fn main() {
    let v = vec_new()        // Vec<?>
    vec_push(v, 10)          // Vec<i64> — типът се фиксира
    vec_push(v, 20)
    print(vec_len(v))        // 2
    print(vec_get(v, 0))     // 10

    let sv = vec_new()
    vec_push(sv, "здравей")  // Vec<str>
    print(vec_get(sv, 0))    // здравей

    let fv = vec_new()
    vec_push(fv, 1.5)        // Vec<f64>
    print(vec_get(fv, 0))    // 1.5
}
```

Смесването на типове се хваща от checker-а:

```baga
let v = vec_new()
vec_push(v, 10)
vec_push(v, "грешка")   // ГРЕШКА: vec_push: елемент от тип str, но векторът е Vec<i64>
```

Поддържани елементни типове: `i64` (и `i32`, приет като `i64`), `str`, `f64`,
`bytes` (двоично безопасен; елементите са box-нати, както `bytes`
стойностите в `Map`) и **struct типове** — `Vec<Line>` и т.н. Struct
елементите са box-нати копия: `vec_push`/`vec_set` копират стойността
навътре, `vec_get` я копира навън (промяна по върнатото копие не пипа
вектора; референтните полета като `Vec`/`Map` остават споделени, както при
обикновено struct присвояване). Смесването на два различни struct типа в
един вектор е грешка при компилация, както при скаларите. Работи и в двата
бекенда (LLVM ползва същите box helper-и; оракъл: `examples/vec_struct.baga`).
Елементният тип е свойство на типа на мястото на свързването.

`Vec<T>` е валиден тип навсякъде, където тип може да се пише — параметри,
`let` анотации, връщани типове и spec `input:`/`output:`. Анотацията носи
елементния тип през границата на функцията, така че `vec_get` връща `T`,
а `vec_push` с друг тип е грешка при компилация:

```baga
fn сума(v: Vec<i64>) -> i64 {
    let mut s: i64 = 0
    for i in 0..vec_len(v) {
        s += vec_get(v, i)     // i64 — от анотацията, не от push
    }
    return s
}
```

`Vec` без `<T>` си запазва старото поведение: неизвестен елемент, при
`vec_get` — историческият подразбиращ се `i64`. Елемент, различен от
`i64`/`str` в анотация (`Vec<f64>`), е грешка при компилация.

### 12.5 Карти (динамични ключ–стойност таблици)

`Map` е хеш-таблица в heap-а. Ключовете са `i64`, `str` или `bytes`; стойностите —
`i64`, `str`, `f64`, `bytes` или struct тип, фиксирани при първия
`map_set` (или с анотация `Map<K, V>`), точно като елементния тип на
`Vec`. Картите са указатели: подадена към функция, картата е споделена и
мутациите се виждат от извикващия. Стойности `bytes` са binary-safe
(NUL/0xFF) — residual I/O буфери (chatbaga) и всякакъв бинарен store.
Struct стойностите са box-нати копия, както `Vec<struct>`: `map_set`
копира навътре, `map_get` — навън; референтните полета (`Vec`/`Map`)
остават споделени.

| Сигнатура | Описание |
|-----------|----------|
| `map_new() -> Map` | празна карта; типовете са неизвестни до първата употреба |
| `map_set(m, ключ, стойност)` | вмъква или презаписва; фиксира/проверява типовете |
| `map_get(m, ключ) -> стойност` | стойността; `0` / `""` / `0.0` / празни `bytes` / нулев struct при липсващ ключ |
| `map_has(m, ключ) -> i64` | `1` ако ключът съществува, иначе `0` |
| `map_del(m, ключ)` | премахва ключа (нищо при липсващ) |
| `map_len(m) -> i64` | брой записи |
| `map_keys(m) -> Vec` | всички ключове — `Vec<str>` / `Vec<i64>` / `Vec<bytes>` според ключа |

```baga
fn брой(m: Map<str, i64>, дума: str) {
    map_set(m, дума, map_get(m, дума) + 1)
}

fn main() {
    let брояч: Map<str, i64> = map_new()
    брой(брояч, "бага")
    брой(брояч, "бага")
    print(map_get(брояч, "бага"))    // 2

    let мета = map_new()              // чист Map: типовете се фиксират при първия set
    map_set(мета, "версия", "0.8")
    print(map_get(мета, "версия"))    // 0.8
}
```

Смесване на ключови или стойностни типове в една карта е грешка при компилация:

```
map_set: стойност от тип str, но картата е Map<str, i64>
```

Липсващ ключ връща нулевата стойност — използвайте `map_has`, ако трябва да
различите „липсва" от „записана нула". При struct стойности нулевият struct
е безопасен по полета: `str` полетата са `""` (не NULL), `Vec`/`Map`
полетата са NULL, но `vec_len`/`map_len` търпят NULL и връщат 0. И двата
бекенда реализират картите нативно (верижна хеш-таблица, расте при
коефициент на запълване 3/4): C бекендът емитира runtime-а в preamble-а,
LLVM бекендът строи същите функции като лениви IR (оракъл:
`examples/map.baga`).

### 12.6 Функционални стойности и ламбди (L5)

Функциите са първокласни стойности. Функционална стойност е типизирана
`fn(T, ...) -> R` (с ефекти: `fn(i64) -> i64 !IO`) и може да живее в
локални променливи, параметри, връщани типове и като елементи на
`Vec`/`Map` (методни таблици).

```baga
fn add(a: i64, b: i64) -> i64 { return a + b }

fn apply(h: fn(i64) -> i64, x: i64) -> i64 { return h(x) }

fn main() {
    let f = add                       // именувана референция
    let g: fn(i64, i64) -> i64 = sub  // с анотация
    print(f(2, 3))                    // 5

    let n = 10
    let lam = fn [n] (x: i64) -> i64 { return x + n }   // ламбда
    print(apply(lam, 5))              // 15

    let ops: Vec<fn(i64) -> i64> = vec_new()            // fn в контейнери
    vec_push(ops, lam)
    print(vec_get(ops, 0)(7))         // 17
}
```

- **Capture-ите са явни и по стойност**: `fn [a, b] (x: i64) -> i64 { ... }`
  копира `a`/`b` в closure-а; по-късна промяна на източника не се
  отразява. `Vec`/`Map` captures споделят референцията (както навсякъде).
- Ефектите на ламбдата пътуват с типа ѝ: wrap в чиста анотация
  (`let g: fn() -> i64 = do_io`) е грешка при компилация.
- Модулно-уточнени референции работят: `let q = http_client.http_get` (L6).
- Fn-локална не може да засенчи глобална функция (пази `--verify` sound);
  извикванията през стойности са непрозрачни за верификатора (честен skip).
- И двата бекенда представят fn стойностите като `(code, env)` handle-и
  (`cell2` от par runtime-а): C бекендът емитва `__clo` wrapper-и в
  preamble-а, LLVM ги строи като лениви IR функции.

### 12.7 Мутатори на `bytes` (S2)

`bytes` буферите се строят и мутират с три вградени функции:

| Сигнатура | Описание |
|-----------|----------|
| `bytes_new(n: i64) -> bytes` | нов нулиран буфер от `n` байта; `n < 0` се свежда до 0 |
| `bytes_set(b: bytes, i: i64, v: i64) -> void` | запис с проверка на границите — при OOB прекъсва с `baga: bytes_set: индекс N извън границите [0, L)`; `v` се маскира до байт (`& 255`). **Мутира споделения буфер** — алиасите виждат записа (семантика като Vec/Map). |
| `bytes_push(b: bytes, v: i64) -> bytes` | връща **нов** `bytes` с дължина `len+1` и `v` накрая; изходният буфер не се пипа. O(n) копие на push — ОК за строене на кадри, не за горещи цикли. |

```baga
let buf = bytes_new(4)
bytes_set(buf, 0, 255)
let alias = buf
bytes_set(alias, 1, 7)
print(bytes_at(buf, 1))            // 7 — set-ът се вижда през алиаса

let f = bytes_push(bytes_push(bytes_new(0), 137), 1)
let g = bytes_push(f, 2)           // f си остава len 2; g е нов len-3 буфер
```

И двата бекенда поддържат трите мутатора (LLVM ги строи като лениви IR;
съобщенията за граници са байтово същите като в C бекенда).

### 12.8 `drop` и памет (MEM-1)

Baga алокира от bump арена, която сама по себе си не освобождава — ОК за
кратки run-ове, фатално за сървъри. `drop(x)` е вградената функция за
ръчно освобождаване: тя освобождава heap блоковете на стойността **веднага**,
а checker-ът гарантира, че никога повече не можете да я пипнете.

```baga
fn main() {
    let v = vec_new()
    vec_push(v, 1)
    drop(v)                    // буферът + struct-ът са освободени
    print(vec_len(v))          // грешка при компилация: използване на 'v' след drop
}
```

`drop` приема само **let-локална променлива** от тип `Vec`, `Map`, `bytes`
или `fn`. Освобождаването е дълбоко:

- **Vec**: елементните кутии (за `bytes`/struct елементи), буферът с данни,
  Vec struct-ът.
- **Map**: кутиите по стойности (за boxed struct стойности), записите,
  кофите, Map struct-ът.
- **bytes**: буферът с данни.
- **fn**: malloc-натият `(code, env)` cell handle. **Env кутията на
  closure-а остава в арената** — може да е споделена с други fn стойности,
  затова не се освобождава (документирано, не скрито).

#### Правила на checker-а (всички са грешки при компилация)

- **Използване след drop** — всяко по-късно четене на променливата:
  `използване на 'x' след free` (същият текст и след `arena_free`).
- **Повторен drop** — `повторен drop на 'x'`.
- **Drop на параметър** — параметрите споделят буфера на извикващия за
  Vec/Map, затова освобождаването би оставило висящ указател там:
  `drop на параметър 'x' — параметрите споделят буфера на извикващия`.
- **Drop на заснета от ламбда променлива** — capture на `x` в ламбда я
  маркира (capture-ите на Vec/Map споделят референцията по §12.6); drop
  след това — вътре или извън ламбдата — се отхвърля:
  `'x' е заснет от ламбда — drop би оставил висящ указател`.
- **Drop в цикъл на променлива, декларирана извън него** — втората
  итерация би била use-after-drop:
  `drop на външна за цикъла променлива 'x' — втората итерация би била use-after-drop`.
  Drop на loop-локални е ОК (пресни са на всяка итерация).
- **Drop на `str` или скалари** — данните на `str` са в арената/интернирани,
  скаларите не притежават heap:
  `drop: неподдържан тип ... — drop е за Vec/Map/bytes/fn`.
- **Drop на не-локален израз** — `drop(vec_new())`, `drop(f(x))`:
  `drop очаква локална променлива (let), не израз`.

#### Клонове: само сигурности

След `if` променлива се смята за drop-ната само ако е drop-ната на
**всички** разклонения. Използването ѝ след сливане, при което само един
клон я е drop-нал, е позволено — checker-ът разсъждава в сигурности, не в
вероятности:

```baga
let v = vec_new()
if n > 0 { drop(v) }          // else-клонът пази v жива
print(vec_len(v))             // OK — maybe-dropped не е definitely-dropped
```

#### Честни граници (v1)

- **Съживяването чрез присвояване остава грешка**: `drop(v); v = vec_new(); use(v)`
  пак се отхвърля — checker-ът е консервативен и държи `v` мъртва.
- **Алиасингът е договор на програмиста**: checker-ът следи *променливи*,
  не heap графи. `let y = x; drop(x); use(y)` **не** се диагностицира —
  точно като в C, drop на `x` докато алиас е жив е ваша отговорност.
  Същото важи и за стойности, скатани в други контейнери
  (`vec_push(v2, x)`-стил споделяне на str/bytes елементи).
- **Вътрешните bytes/str буфери на освободените кутии остават в арената** —
  може да са споделени (`str` елемент, интерниран другаде), затова дълбокият
  walker не ги освобождава.
- **Блокове > 1024 B не се reclaim-ват** от free list-а (по-долу).
- **Историческият боклук остава**: стари буфери, изоставени от `vec_grow` /
  `map_rehash`, не се следят; `drop` освобождава само *текущите* блокове.
- **Течове при изход от scope НЕ се диагностицират** — компилаторът няма
  severity „предупреждение", затова стойност, излязла от scope без `drop`,
  мълчаливо тече в арената. Ловът на течове е територия на MEM-3 (региони).
- **LLVM бекенд**: честен `unsupported` за `drop` (само C бекенд).

#### Runtime: free list

`baga_alloc` държи free list-ове по размерни класове за блокове
**≤ 1024 B** (16 B грануларност, 64 класа, подравнени алокации) плюс
pow2 класове до 32 MiB (R18); освободените блокове се преизползват преди
bump пойнтърът да напредне. От R52 арената и двата free-list слоя са
**thread-local** (`__thread`) — старият глобален alloc mutex
сериализираше всяка `go`/`go_bg` нишка (де-факто GIL). Доказателството,
че работи: цикъл с 1M итерации alloc+drop държи maxrss ~6.2 MB срещу
~87.6 MB без `drop`.

#### MEM-2: облигации на верификатора (`--verify`)

Статичният верификатор следи `HK_DROP` ghost състояние по име на
променлива (същата handle-протоколна машинерия като `spawn → join | detach`
на M14): `let x = vec_new()/map_new()/bytes_new(...)` регистрира `x` като
жива, `drop(x)` я превключва в drop-ната, а използване след drop или
повторен drop по жива пътека е **ОБРОЧЕНО (REFUTED)** с контрапример
(`examples/verify/mem_drop.baga`). Алиасингът и drop на fn стойност са
мълчаливи no-claim пътеки, а програми извън поддържания фрагмент се
прескачат честно — същият gating като M14.

#### MEM-3 lite: seatbelt за arena handle

`arena_free(a)` маркира локалния handle `a` по същия начин като `drop`:

- **двоен free** — `повторен arena_free на 'a'`;
- **alloc/reset след free** — `използване на арена 'a' след arena_free`;
- **всяка употреба на `a` след free** — `използване на 'a' след free`.

**Region tags:** `let p = arena_alloc(a, n)` свързва `p` с арената `a`.
След `arena_free(a)` употребата на `p` е `използване на 'p' след free`.
Само директни `arena_alloc` свързвания се маркират (не аритметика върху
указателя).

## 13. Ефектова система

Ефектите са *измерения на типа*. Функция, която извършва IO, не връща просто
`str`; тя връща `str !IO`. Компилаторът следи тези маркери и отказва да компилира
код, който ги пренебрегва.

### 13.1 Деклариране на ефекти

Ефектите се изброяват след връщания тип, всеки с префикс `!`:

```baga
fn прочети(път: str) -> str !IO !NotFound {
    return read_file(път)
}
```

Имената на ефектите са обикновени идентификатори (`IO`, `NotFound`,
`Permission`, ...). Вие определяте речника; компилаторът налага отчитането.

### 13.2 Разпространяване с `?`

Постфиксният оператор `?` изпълнява ефектен израз и *разпространява* ефектите му
към обграждащата функция. Тогава тя трябва или да декларира тези ефекти, или да
ги хване.

```baga
fn обработи(път: str) -> str !IO !NotFound {
    let данни = прочети(път)?   // ефектите изтичат нагоре в 'обработи'
    return данни
}
```

### 13.3 Обработка с `catch`

`catch` премахва едно измерение на ефекта, като предоставя резервна стойност:

```baga
expr catch !Effect => резерва
```

Нареждайте няколко `catch` клаузи, за да обработите няколко ефекта:

```baga
fn main() {
    let съдържание = прочети("данни.txt")
        catch !NotFound => "празно"
        catch !IO => "грешка"
    print(съдържание)
}
```

След като и двата ефекта са хванати, изразът е обикновен `str` без оставащи
ефекти, затова `main` (която връща `void`, без ефекти) минава проверка на
типовете.

### 13.4 Грешката за необработен ефект

Ако ефект стигне до функция, която нито го декларира, нито го хваща,
компилаторът съобщава:

```
file.baga: 4:1: необработен ефект !IO във 'main' — декларирай го в return типа или го хвани с catch
```

Това е сърцевината на системата: ефектите не могат да бъдат премълчани.

### 13.5 `!Overflow` — ефект, който верификаторът извежда

`!Overflow` е специално измерение на ефекта: за разлика от `!IO` (което се
*генерира* от вградени функции като `read_file`), `!Overflow` не се генерира от
никой builtin — той се **декларира** и се **разпространява** като всеки ефект,
а необходимостта му се открива от статичния верификатор (`--verify`, M15/M18).

```baga
fn inc(n: i64) -> i64 !Overflow {   // "може да прелее i64"
    return n + 1
}
```

Семантиката (M18): ефектът е *разрешение*, не твърдение.

- Функция **без** `!Overflow` твърди, че е безопасна към преливане. `--verify`
  проверява това: доказва го (всички аритметични задължения са безопасни),
  оборва го с контрапример (ако прелива, а ефектът не е деклариран — ненулев
  exit), или честно НЕ МОГА ДА РЕША.
- Функция **с** `!Overflow` обявява риска честно — верификаторът пак отпечатва
  преливането като доказателство, но то вече не е нарушение (exit 0);
  `ensures` вердиктите са в идеализирания ℤ модел.
- `!Overflow` се разпространява през извиквания: който вика `!Overflow`
  функция, трябва да декларира или хване ефекта (същата грешка
  „необработен ефект !Overflow").

`--proofs` извежда теорема `<fn>_overflow_safe`; `--verify --json` добавя поле
`overflow_effect`. За пълната теория виж `docs/thesis-m18-overflow-effect.md`.

## 14. Система за спецификации

`spec` описва *какво* трябва да прави функцията; тялото на функцията описва
*как*. Компилаторът проверява, че спецификацията и функцията съвпадат по форма,
и записва гаранциите на spec-а за извличане на доказателства.

```baga
spec сортирай {
    input:
        arr: i64
    output: i64
    guarantees:
        - output is sorted
        - output has same elements as input
}

fn сортирай(arr: i64) -> i64 {
    return arr
}
```

### 14.1 Структура на спецификация

```
spec <име> {
    input:
        <параметър>: <тип>
        ...
    output: <тип>
    guarantees:
        - <гаранция в свободен текст>
        - <гаранция в свободен текст>
}
```

- `<име>` на spec-а трябва да съвпада с името на съществуваща функция.
- `input` изброява параметрите; броят и типовете им трябва да съвпадат с
  функцията.
- `output` е връщаният тип; трябва да съвпада с връщания тип на функцията.
- `guarantees` са редове в свободен текст, всеки започващ с `-`. Те документират
  договора и се показват от `--proofs` и `--specs`.

### 14.2 Какво проверява компилаторът

Компилаторът отхвърля програма, когато spec не съвпада с функцията си:

| Несъответствие | Грешка |
|----------------|--------|
| Spec сочи несъществуваща функция | `spec '<име>' описва функция, която не съществува` |
| Различен брой параметри | `spec '<име>': input има N параметъра, но функцията има M` |
| Различен тип на параметър | `spec '<име>': параметър '<p>' е A в spec-а, но B във функцията` |
| Различен изходен тип | `spec '<име>': output е A, но функцията връща B` |

Самите гаранции все още не се доказват формално; `--proofs` ги отпечатва със
статус `UNVERIFIED — requires formal proof or testing`.

### 14.3 Изпълними гаранции (`ensures:`)

Секцията `ensures:` съдържа булеви изрази на Бага, разделени със запетаи.
В тях са видими имената на input параметрите и `output` — върнатата стойност.
Компилаторът тип-проверява всеки израз (трябва да е `bool`) и го компилира до
runtime проверка, която се изпълнява след всяко повикване на функцията —
включително рекурсивните. При нарушение програмата спира:

```
spec 'удвой': ensures #1 нарушена: output == 2 * x
```

```baga
spec факториел {
    input:
        n: i64
    output: i64
    ensures:
        output > 0,
        n <= 1 || output >= n
}
```

`guarantees:` остава документация в свободен текст (статус UNVERIFIED в
`--proofs`); `ensures:` се изпълнява (статус RUNTIME-CHECKED). `ensures` върху
функция без върнат тип е грешка при компилация. LLVM backend-ът също изпълнява
`ensures` (и `requires`) — същият wrapper pattern като C backend-а.

### 14.4 Предусловия (`requires:`)

Секцията `requires:` съдържа булеви изрази върху input параметрите, разделени
със запетаи. Те се тип-проверяват при компилация и се изпълняват **преди**
тялото на функцията при всяко повикване. При нарушение програмата спира:

```
spec 'корен': requires #1 нарушено: x >= 0
```

```baga
spec корен {
    input:
        x: i64
    output: i64
    requires:
        x >= 0
    ensures:
        output >= 0
}
```

`requires` е позволен и върху функции без върнат тип (за разлика от `ensures`,
което изисква `output`). В requires изразите `output` не е видим.

### 14.5 Property-based тестване (`--test-specs`)

`baga --test-specs файл.baga` не изпълнява `main`, а генерира тестов драйвър,
който вика всяка функция с `ensures`/`requires` 100 пъти с детерминистични
случайни входове (фиксиран seed — повторяеми прогони). `requires` филтрира
невалидните входове (драйвърът генерира нови, докато не намери валиден);
нарушение на `ensures` е контрапример и спира програмата с входа:

```
spec 'удвой': ensures #1 нарушена: output == 2 * x
  вход: -347
```

Поддържат се функции с входове само от тип `i64` и/или `bool`; останалите се
пропускат със съобщение. Домейнът на договора е част от договора — например
`факториел` ограничава `n <= 20`, защото `i64` прелива след това.

## 15. Извличане на доказателства

`baga --proofs <файл>` отпечатва четими доказателствени скици, извлечени от
AST-то:

```
proofs for факториел:
  theorem факториел_signature:
    ∀ n: i64. факториел(n) → i64

  theorem факториел_terminates:
    ∀ n: i64. terminates(факториел(n))
    evidence: base case with early return, 2 return paths

  theorem факториел_pure:
    факториел is pure (no declared effects)
```

За всяка функция компилаторът издава теорема за сигнатурата, скица за
завършване (с доказателства като базови случаи и брой пътища за връщане) и
теорема за чистота/ефекти. Ако има spec, гаранциите му също се изброяват.

```baga
fn факториел(n: i64) -> i64 {
    if n <= 1 {
        return 1
    }
    return n * факториел(n - 1)
}

fn main() {
    print(факториел(10))   // 3628800
}
```

### 16.3 Фибоначи (цикъл while)

```baga
fn фибоначи(n: i64) -> i64 {
    let mut a: i64 = 0
    let mut b: i64 = 1
    let mut i: i64 = 0
    while i < n {
        let temp = b
        b = a + b
        a = temp
        i = i + 1
    }
    return a
}

fn main() {
    for i in 0..15 {
        print(фибоначи(i))
    }
}
```

### 16.4 Сумиране с цикъл for

```baga
fn main() {
    let mut сума: i64 = 0
    for i in 1..101 {
        сума += i
    }
    print(сума)   // 5050
}
```

### 16.5 Извеждане на типове и разширяване

```baga
fn кръг_лице(r: f64) -> f64 {
    return 3.14159265 * r * r
}

fn main() {
    let r: f64 = 5.0
    print(кръг_лице(r))

    let x = 10        // i64
    let y = 3.5       // f64
    print(x + y)      // f64

    let по_голямо = x > 5
    print(по_голямо)  // true
}
```

### 16.6 Структури и достъп до полета

```baga
struct Точка { x: f64, y: f64 }

fn разстояние(a: Точка, b: Точка) -> f64 {
    let dx = a.x - b.x
    let dy = a.y - b.y
    return dx * dx + dy * dy
}

fn main() {
    let a = Точка { x: 0.0, y: 0.0 }
    let b = Точка { x: 3.0, y: 4.0 }
    print(разстояние(a, b))   // 25
}
```

## 17. Съобщения за грешки

Грешките се печатат във формат `файл: ред:колона: съобщение`. Съобщенията са на
български.

### 17.1 Лексикални грешки

| Съобщение | Значение |
|-----------|----------|
| `незатворен низ` | Незатворен низов литерал. |
| `незатворен символ` | Незатворен символен литерал. |
| `непозната escape последователност` | Непозната escape последователност в низ/символ. |
| `непознат символ '<c>' (0xNN)` | Символ, който лексерът не разпознава. |

### 17.2 Синтактични грешки

| Съобщение | Значение |
|-----------|----------|
| `очаквах '<X>', получих '<Y>'` | Очакван е токен X, но е намерен Y. |
| `очаквах израз, получих '<Y>'` | Очакван е израз, но е намерен Y. |
| `очаквах декларация (fn, struct, spec), получих '<Y>'` | На горното ниво се допускат само декларации. |

### 17.3 Типови и семантични грешки

| Съобщение | Значение |
|-----------|----------|
| `повторно дефиниране на '<име>'` | Името е декларирано повторно в същата област. |
| `недефинирана променлива '<име>'` | Използване на недефинирана променлива. |
| `непозната функция '<име>'` | Извикване на непозната функция. |
| `'<име>' очаква N аргумента, получих M` | Грешен брой аргументи. |
| `'<име>': аргумент #N е от тип A, но параметърът е B` | Аргумент от несъвместим тип към потребителска функция (`i32`/`i64` са съвместими). |
| `аритметична операция върху не-числови типове (A, B)` | `+ - * / %` приложени върху не-числови операнди. |
| `очаквах bool в условие, получих A` | Условието на `if` не е булево. |
| `очаквах bool в условие на while, получих A` | Условието на `while` не е булево. |
| `непознато поле '.<име>'` | Полето не съществува в структурата. |
| `непознат struct '<име>'` | Структурен литерал за недекларирана структура. |
| `връщам A, но функцията очаква B` | Върнатият тип не съвпада с декларирания. |
| `vec_push: елемент от тип A, но векторът е Vec<B>` | Смесване на елементни типове в един `Vec` (и за `vec_set`). |
| `vec_push: неподдържан елементен тип A за Vec (поддържат се i64, str, f64, bytes и struct)` | Елемент, различен от `i64`/`str`/`f64`/`bytes` (и за `vec_set`). |
| `Vec<T>: неподдържан елементен тип A (поддържат се i64, str, f64, bytes и struct)` | Анотация `Vec<A>` с елемент, различен от `i64`/`str`/`f64`/`bytes`. |

### 17.4 Ефектови грешки

| Съобщение | Значение |
|-----------|----------|
| `необработен ефект !<E> във '<fn>' — декларирай го в return типа или го хвани с catch` | Ефект е стигнал до функция, която нито го декларира, нито го хваща. |

### 17.5 Грешки в спецификации

| Съобщение | Значение |
|-----------|----------|
| `spec '<име>' описва функция, която не съществува` | Няма функция с името на spec-а. |
| `spec '<име>': input има N параметъра, но функцията има M` | Разлика в броя параметри. |
| `spec '<име>': параметър '<p>' е A в spec-а, но B във функцията` | Разлика в типа на параметър. |
| `spec '<име>': output е A, но функцията връща B` | Разлика във връщания тип. |
| `spec '<име>': ensures изисква функция с върнат тип` | `ensures` върху void функция. |
| `spec '<име>': ensures #N е A, очаквах bool` | Ensures изразът не е булев. |
| `spec '<име>': requires #N е A, очаквах bool` | Requires изразът не е булев. |

### 17.6 Структура на програмата

| Съобщение | Значение |
|-----------|----------|
| `липсва функция 'main'` | Програмата няма функция `main`. |

## 18. Команден ред на компилатора

```
baga [опции] <файл.baga>
```

Без опции Бага генерира C, компилира го с `gcc -O2`, изпълнява получения
двоичен файл и почиства временните файлове.

| Флаг | Описание |
|------|----------|
| *(няма)* | Компилирай и изпълни. |
| `--emit-c` | Изпечатай генерирания C код на stdout; не компилирай. |
| `--ast` | Изпечатай построения AST (debug). |
| `--tokens` | Изпечатай потока от токени (debug). |
| `--specs` | Изпечатай документацията за spec-ове, извлечена от източника. |
| `--proofs` | Изпечатай извлечените доказателствени скици. |
| `--test-specs` | Property-based тестване на spec договорите (случайни входове, детерминистичен seed). |
| `--verify` | Статична верификация на requires/ensures договорите. |
| `--json` | Машинно-четим JSON изход (с `--verify`). |

### 18.1 Импорти и пакети (sandak)

`import "път/към/файл.baga"` в началото на файла вмъква друг файл текстуално
(с include guard и детекция на цикли). Търсенето по ред: (1) релативно на
текущия файл, (2) във всяка `-I` директория в реда на подаване, (3) релативно
на работната директория.

**Namespaces.** Всеки импортиран файл е и *модул* с името на файла без
`.baga` (`std/net/http_client.baga` → модул `http_client`), а функциите му
могат да се извикват уточнено: `http_client.http_get(url)`. Два модула
могат да имат функции с еднакво име — това е легално и всяка дефиниция
получава уникален вътрешен символ (`модул.име`). При **неуточнено**
извикване редът е: (1) печели дефиницията от текущия файл, (2) иначе
единственият импортиран модул с такава функция, (3) иначе грешка при
компилация със списък на кандидатите (`нееднозначно извикване на 'f' …`).
Локална променлива с име на модул го засенчва (field достъпът си работи).
Две функции с еднакво име в *един* модул са checker грешка (`повторна
дефиниция`); forward декларация (`fn f(...)` без тяло) + една реализация
са ОК. **Struct имената следват същите модулни правила**: два модула могат
да имат `struct Rec` — собственият файл печели локално, а отвън се уточнява
с `util2.Rec` (в типови анотации и литерали); неуточнена двусмислена
референция е checker грешка с подсказка. Дублиран struct в един модул е
checker грешка. Enum имената остават глобални (дубликат между модули е
ясна checker грешка, не gcc такава), както и референциите на worker
функции в `go`.

**Import alias.** `import "modb/util.baga" as util2` преименува модула:
функциите му се извикват `util2.f()`, а подсказките за нееднозначност
ползват alias-а. Това е изходът, когато два импортирани файла имат еднакъв
basename (`moda/util.baga` срещу `modb/util.baga` — и двата биха били
модул `util` и едноименните им функции биха се счели за „дубликати в един
модул"). Един alias на файл: повторен import със същия alias е идемпотентен,
различен втори alias е грешка при компилация.

В пакетиран проект импортът носи името на пакета — `import "fmrbaga/app.baga"`,
`import "std/str/str.baga"` — а `-I` флаговете се изчисляват автоматично от
пакетния мениджър **sandak** според `sandak.toml` манифестите на зависимостите
(`sandak fetch` / `sandak build` / `sandak run`; виж README, „Packages — sandak").
