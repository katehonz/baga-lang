# Бага — езикът, в който компилаторът е съдията

**Бага** (⚔️) е език за програмиране за системен и продуктов код в ерата на изкуствения интелект. Основната му идея е проста: пишете нормални програми, а компилаторът държи **ефектите, спецификациите и доказателствените скици** видими, така че човек (или агент) да може да се довери на резултата.

> *„Въпросът не е „какво е ново". Въпросът е „какво още не е слепено заедно"."*

Името идва от българската дума „бага" — воин, който се бие сам. Езикът тръгва от едно наблюдение: нищо в програмирането не е ново, но правилната рекомбинация в правилния момент може да бъде. Rust е линейна логика (1987) + регионно управление на паметта (1994) + Cyclone (2001). Haskell е практична теория на категориите. Въпросът за Бага беше: **какво още не е слепено?**

Отговорът: език, проектиран за работния процес, в който **AI пише имплементацията, а компилаторът е съдията** — съдия, който може да *доказва*, а не само да проверява типове.

## Трите стълба

### 1. Спецификациите са граждани от първи ред — и се налагат статично

Човекът пише спецификацията. AI пише имплементацията. Компилаторът **доказва или оборва имплементацията спрямо спецификацията, статично, преди каквото и да е да се изпълни**:

```baga
spec sum_to {
    input:
        n: i64
    output: i64
    requires:
        n >= 0
    ensures:
        0 <= output
    decreases:
        n
}

fn sum_to(n: i64) -> i64 {
    if n < 1 { return 0 }
    let r = sum_to(n - 1)
    return n + r
}
```

```bash
$ ./baga --verify term_dec.baga
```

```
verify sum_to:
  ensures #1 (0 <= output): ДОКАЗАНО
  (терминация: доказана чрез decreases — пълна коректност)
```

И когато AI сгреши, не получава предупреждение — получава **оборване с конкретен контрапример**:

```
verify bad_abs:
  ensures #1 (output >= 0): ОБРОЧЕНО
    контрапример: x = -1
```

Това не е Design by Contract (Eiffel, 1986) с проверки по време на изпълнение. Не е и черна кутия със SMT солвер: верификаторът е малък, проверим двигател (елиминация на Фурие–Моцкин над рационалните числа + символно изпълнение + правила на Хоар), който е **коректен по конструкция**. Единственият път до ДОКАЗАНО е да се покаже, че отрицанието на задължението е неизпълнимо дори над рационалните числа, което предполага неизпълнимост над целите. Всичко извън фрагмента честно се отчита като НЕИЗВЕСТНО — никога фалшиво доказано. Всеки контрапример се пре-проверява с директно изчисление и минава през **врата за заключителност**: входовете трябва да нарушават договора за *всяка* стойност на вътрешните абстрактни променливи — иначе отговорът е НЕИЗВЕСТНО, а не фалшива тревога.

Витрината: **факториел, напълно доказан** — рекурсивна, нелинейна функция, с терминация, без нито един SMT солвер:

```baga
spec fact {
    input: n: i64
    output: i64
    requires: n >= 0
    ensures: output >= 1
    decreases: n
}

fn fact(n: i64) -> i64 {
    if n <= 0 { return 1 }
    let r = fact(n - 1)   // индукционна хипотеза: r >= 1
    return n * r          // n >= 1, r >= 1 ⇒ n * r >= 1
}
```

И понеже потребителят е AI агент, съдията има машинен интерфейс:

```bash
$ ./baga --verify --json bad_abs.baga
```

```json
{"functions": [{"name": "bad_abs", "ensures": [{"text": "output >= 0",
  "result": "refuted", "counterexample": [{"name": "x", "value": -1}]}], ...}]}
```

Примката се затваря сама: агентът излъчва код → `baga --verify --json` → оборено с контрапример → агентът поправя → ДОКАЗАНО. Без LLM да съди LLM.

### 2. Грешките са измерения на типа, не изключения

```baga
fn read_file(path: str) -> str !IO !NotFound {
    let handle = open(path)?      // !IO, !NotFound се разпространяват
    let content = read(handle)?   // !IO, !Permission се разпространяват
    content
}

fn main() {
    let content = read_file("data.txt")
        catch !NotFound => "empty"
        catch !IO => "error"
    print(content)
}
```

`str !IO !NotFound` е **различен тип** от `str`. Ефектите се композират автоматично при извикване на функции. Необработените ефекти са **грешки по време на компилация**:

```
error: unhandled effect !IO in 'main' — declare it in the return type or catch it
```

Това е ефектна система (Плоткин и Пауър, 2003) с явен полиморфизъм на ефекти и извод на ефекти. Koka го прави академично. Бага го прави практически. Операторът `?` разпространява ефекти, `catch !E => handler` премахва ефект от множеството, а множествата от ефекти образуват полурешетка под обединение.

### 3. Компилаторът извлича доказателства от кода ви

```bash
$ ./baga --proofs examples/faktorial.baga
```

```
proofs for факториел:
  theorem факториел_signature:
    ∀ n: i64. факториел(n) → i64

  theorem факториел_terminates:
    ∀ n: i64. terminates(факториел(n))
    evidence: base case with early return, 2 return paths

  theorem факториел_pure:
    факториел is pure (no declared effects)
```

Не Coq. Не Lean. **Четим текст**, който човек (или AI) може да провери — а теоремите за договорите са подкрепени от статичния верификатор, а не са просто извлечени пожелания. Това е **обратното** на извличането на доказателства в Coq: Coq извлича програми от доказателства, а Бага извлича доказателствени скици от програми.

## Защо сега?

Всяка голяма част от AI-инструментариума за код днес има една и съща форма: LLM генерира код, а след това нещо проверява дали кодът съответства на намерението. Това „нещо" обикновено е:

- тестове (непълни по конструкция — извадка от входното пространство),
- друг LLM (LLM съди LLM — кръгова логика),
- човек (тясното място, което се опитвахме да премахнем).

Rust отговори на въпроса „как да предотвратим сегфолтове". Добър отговор. Но въпросът през 2026 г. не е „как да предотвратим сегфолтове", а **„как да се доверим на код, който не сме писали"**. Индустрията вече се е съгласила с диагнозата: Microsoft официално промотира **Spec-Driven Development (SDD)** като основа на AI-нативното инженерство — спецификацията като *споделен източник на истина* за хора и AI. Разликата е в нивото: SDD атакува загубата на намерение на ниво **процес** (документ + стъпка Validate), а Бага прави по-силния ход — спецификацията е **езикова конструкция**, а съответствието е **присъда по време на компилация**. В спектъра spec-first → spec-anchored → spec-as-source, Бага е далечният край: *spec-as-source*.

## Самият език

```baga
// Да, кирилските идентификатори работят. Езикът е идентичност.
fn факториел(n: i64) -> i64 {
    if n <= 1 { return 1 }
    n * факториел(n - 1)
}

fn main() {
    for i in 0..15 {
        print(факториел(i))
    }
}
```

Характеристики: `fn`, `let`/`let mut`, `if`/`else`, `while` (с инварианти на цикъла), `for..in`, `match`, структури, изброими типове, `str`, `i64`, `f64`, `bool`, `bytes`, `Vec`, интерполация на низове, ефекти (`!IO`, `?`, `catch`), спецификации с `requires`/`ensures`/`decreases`, извличане на доказателства, FFI (`extern fn`), импортиране на пакети.

## Компилира сам себе си

```
C bootstrap → compiler.baga → C → gcc → baga2
baga2       → compiler.baga → C → gcc → baga3
baga2 == baga3 ✓   (неподвижна точка)
```

Самокомпилиращият се компилатор е **~3200 реда Бага**. C bootstrap-ът е ~10 хиляди реда C с **нула зависимости** (само gcc и make). Има и LLVM IR бекенд (C API на LLVM 14). Доверието е вградено, а не се надява:

- **Самокомпилация до неподвижна точка** — самокомпилаторът се възпроизвежда байт по байт (`make self`).
- **Оракул на бекенда** — изходът на LLVM бекенда се сравнява с този на C бекенда на всеки пример (`lli-14`).
- **Оракул на верификатора** — `--test-specs` тества със свойства всеки договор, който статичният верификатор нарича ДОКАЗАНО; те трябва да съвпадат.
- Всичко това е една команда (`make test`, `make self`) и е свързано с CI.

## Криптография в чист Бага и цяла екосистема

Криптографията е **имплементирана в Бага**, а не свързана с OpenSSL по време на изпълнение: SHA-1/256, HMAC, AES, GCM, HKDF, bn, X25519, P-256/ECDSA, RSA, DER, X.509; TLS 1.3 клиент и `https://` върху чист TLS; JWT (HS256/RS256/ES256) в `app-product/jwtbaga`.

Екосистемата не е от демота, а от **пакети за използване**, строени с пакетния мениджър **sandak** (`sandak.toml` на пакет): httpdbaga (HTTP/1.1 + HTTP/2 + HPACK), pgbaga (PostgreSQL wire клиент), boilaDB (мултимодална SQL база данни), ormbaga (ORM в стил ActiveRecord + миграции), fmrbaga (уеб фреймуърк), rocksbaga (издръжлив LSM KV сторидж), raftbaga (3-възлов Raft консенсус), txnbaga (2PC + MVCC), imgbaga (растерни изображения) и още десетки.

## Бърз старт

```bash
git submodule update --init --recursive
make
./baga examples/zdravei.baga
# Здравей, багатуре. Боят започва.
```

Или в браузъра: `python3 playground/serve.py` → http://localhost:8080

Основният компилатор е с нула зависимости — само `gcc` и `make`. LLVM бекендът е по избор.

## Честен статус

Това е **работен прототип**, не производствен език — но основното твърдение е реално и се проверява за пет минути:

```bash
make && ./baga --verify examples/verify/fact_full.baga
```

Фрагментът на верификатора е умишлено малък и казва НЕИЗВЕСТНО, вместо да гадае; общата нелинейна аритметика (полиноми от по-висока степен, деление с променливи) е оставащото стълбище. Ефектите са само по време на компилация (изтриват се при генериране на код). Езикът се документира на български и английски, лицензът е MIT, а изходният код е на [git.bara-lang.org](https://git.bara-lang.org/baga-lang-ai/baga-lang-ai).
